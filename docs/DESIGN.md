## 1 定位

免安装的单文件 Windows 程序（C# WinForms + 系统自带 csc 编译，与 `permanent-delete-menu` 同技术栈）。
主界面是**多行多列的按钮墙**：点一下按钮 = 启动一个已经做好的程序 / 脚本 / 功能。
加按钮只是往 `tools\*.json` 丢配置，**不需要重新编译主程序**。

- 程序名 **萌新工具箱**；标题栏 `萌新工具箱 v1.2.0`
- 署名 `mxx1` / `mxx1.cn`；许可证 **GPL-3.0-or-later**；仓库 `mxx1-toolbox`
- 独立工程 `D:\萌新工具开发\toolbox\`，与 `permanent-delete-menu` **互不修改**（只调它的 exe）

### 4.0 「常用」（置顶 + 最近使用，112 个按钮里最常用的那几个）

用户 2026-10-04 的反馈之一是"找按钮费劲"：112 个按钮分成 8 个页签，最常用的三五个每次都要翻页。
这一页就是为此加的，**放第 1 个**：

- **置顶**：右键任意按钮 → 「置顶 / 取消置顶」（`pinned.txt`），也可以命令行 `pin` / `unpin <id>`。
- **最近使用**：跑过的按钮自动进列表（`recent.txt`，最新在最上，最多 12 个）；设置窗口有「清空最近使用」。
- 两块分别有自己的小标题（「置顶 · N 个（在按钮上点右键可以取消置顶）」「最近使用 · N 个（最多 12 个）」），
  **空的时候给一句"怎么把它填满"的说明**，不是一片空白（Test-Gui 的 D05f 盯着）。
- 这一页的按钮数是算出来的，所以 `A07 八个页签的按钮数` 里 recent = 0（干净机器上）。

### 4.1 常用设置（33 个，三段，全是真功能）

**33 个都点得动**（`confirm` = 点之前先弹二次确认）：

> **2026-10-04 起，这一页里 12 个"写注册表"的开关都改走 `src\RegEngine.cs`**（和隐私设置共用一份实现，

### 4.5 隐私设置（29 个 = 11 组成对开关 + 4 个权限入口 + 状态 / 优化 / 还原）

后端是 `src\Privacy.cs`：一张「开关 → 注册表值」的表（一个开关可能对应好几个值，
「系统广告」一组就是 8 个）。三条底线：

1. **只碰隐私 / 广告 / 遥测开关**，Defender、防火墙、UAC、SmartScreen 这些安全防线一概不碰 ——
   这条有测试盯着（`I05`：隐私页签上不许出现"关掉安全防线"的按钮）。
2. **写之前先把原值记下来**（`%LOCALAPPDATA%\mxx1-toolbox\privacy-original.tsv`），
   而且只记第一次：反复点「关闭 X」不会把"已经改过的值"当成原值，否则还原出来的是
   "上一次关闭后的状态"而不是出厂状态。原来没有这个值的，还原时把值删掉。
3. **写完必须读回来核对** —— 读了不等于写进去了（「按流量计费」那次踩过"假成功"）。

- **列表显示中文名**（用户 2026-10-04 报的「卸载单个应用里面的窗口是不能显示中文是？」）：`Get-AppxPackage`
  给的 `Name` 是包标识（`Microsoft.WindowsCalculator` 这种），人能看懂的名字在「开始菜单」那一层 ——
  脚本先读 `Shell.Application` 的 `shell:AppsFolder`、再读 `Get-StartApps`，用 **AppID 里 `!` 前面的
  包族名**建映射，列表写成 `计算器　（Microsoft.WindowsCalculator）　·　11.2508.4.0`；
  取不到中文名的（系统组件基本都取不到）就只显示包名。窗口字体设成微软雅黑 9pt。
- **排序：能卸的排前面**：先排非系统包（有中文名的更前），`SignatureKind = System` 的 Windows 组件
  排在**最后**并加 `【系统组件】` 前缀 —— 原来按包名首字母排，一屏 `Microsoft.AAD.BrokerPlugin`
  这种，用户根本不知道哪个能卸。
- 确认框里会写明「这是 Windows 系统组件 / 这台机器没有商店，卸了装不回来」以及
  「系统标记为不可移除，多半会直接失败」（`NonRemovable`）。
- **筛选框的索引坑（会卸错应用）**：列表被过滤之后 `ListBox.SelectedIndex` 和 `$pk` 的下标**不再对应**，
  原来的 `$pk[$idx]` 会让"搜关键字再点卸载"卸掉另一个包。现在过滤时同步维护 `$shown` 数组，
  取的是 `$shown[$idx].Pkg`。
- **列表模式自检**：设 `MXX1_PICKER_LIST_ONLY=1` 时只把列表打到 stdout、不弹窗，于是这条能在命令行
  回归里真跑（`J09`/`J10`/`J11` 分别盯"有中文名""系统组件在最后""只列不卸"）。
- 这台机器上**没有应用商店**（`Microsoft.WindowsStore` 不存在），所以确认框里会明写
  "卸载以后装不回来"。
- **故意不做**：批量卸载、卸载 Edge、卸载 Xbox / 天气 / 邮件 / 地图那一套。批量不可逆、容易误删
  用户自己装的软件，而这台机器上那些预装应用本来就已经被精简掉了。`J06`–`J08` 盯着这个底线。

### 4.7 我的工具（3 个内置按钮 + 用户自己加的按钮）

| 一次拖**多个**文件 | 直接建按钮，名字取文件名 |
| 手写 `%LOCALAPPDATA%\mxx1-toolbox\tools.json` | 同 `id` 覆盖内置按钮；图形化写入的就是这个文件的格式 |

四种类型对应已有的 `kind`：启动程序（`exe`）/ 打开文件夹·网址·系统页面（`open`）/
运行脚本文件（`script` + `path`）/ 运行一行命令（`script` + `inline`）。

- 右键用户自己加的按钮 → **编辑按钮… / 删除按钮**（只对用户层开放，内置按钮不受影响）；
  删除前二次确认，并且只删 `tools.json` 里那一条。
- 每次写入前把旧文件备份成 `tools.json.bak`（手写的注释或特殊字段万一丢了还能捞回来）。
- 存完会重新测量列宽：新按钮名字更长就把窗口加宽，**不会缩窄**。
- 「导出我的按钮」/「导入按钮」（`app.exporttools` / `app.importtools`）：把用户层导成一个 json
  （内置按钮不导出）／把导出文件并回来（同 id 覆盖）。命令行是 `export` / `import`，两条路走的是
  同一份 `UserTools` 代码。
- **置顶**：右键任意按钮 → 「置顶 / 取消置顶」，置顶的按钮排在这一页最前面；id 记在
  `%LOCALAPPDATA%\mxx1-toolbox\pinned.txt`（一行一个，也可以用 `pin` / `unpin` 命令）。
  单独一个文件而不是塞进 `settings.ini`：置顶是一条一条改的，ini 每次都要整份重写。

## 5 按钮行为

1. **左键单击** → 执行（`ClickMode=double` 时改成双击）
2. **悬停/按下** → 浅蓝底 + 蓝边框 / 下沉一色（灰按钮是灰底变深一档，不变蓝）
3. **执行中** → 按钮禁用 + 图标换成转圈图标（**文字一字不改**）；结束时写日志（含退出码），有输出就弹结果窗口
4. **右键** → 运行 / 以管理员身份运行 / 打开所在文件夹 / 复制启动命令 / 查看按钮定义（编辑与排序在 P1）
5. **危险按钮** → 深红文字，点击先弹「确认执行」（默认按钮 = 取消）
6. **灰色占位按钮** → **禁用**（`Enabled=false`）：点不动、不能聚焦、不弹提示；灰底 + 灰字 + 置灰图标，
   状态栏写明「灰色 N 个没接功能」。命令行 `run <id>` 仍然只解释、绝不执行（退出码 0 + `--dry` 报 `kind=none`）。
7. **找不到目标** → 按钮可点但会明确报错（不静默失效）：系统工具缺失报"这台电脑是 Windows 家庭版…"
   这类整句，隔壁 exe 缺失报"请在「设置」里指定它的路径"。
8. **界面动作优先**（关于 / 日志 / 设置 / 新建按钮 / 常用链接）→ 先于占位判断处理（灰按钮已经点不到，这条是给命令行和界面动作留的）。

## 6 按钮的目标类型（`kind`）

| kind | 干什么 | 关键字段 |
| --- | --- | --- |
| `builtin` | 本程序内置功能 | `module`（`permdel` / `system` / `app`）+ `action` + `options` |
| `exe` | 启动外部程序 | `path`, `args`, `workdir`, `runAsAdmin`, `wait`, `timeoutSec` |
| `script` | ps1 / cmd / bat（可内联） | `shell`, `path` 或 `inline`, `runAsAdmin`, `timeoutSec` |
| `open` | 网址 / 文件夹 / 系统设置页 | `target`（支持 `shell:startup`、`ms-settings:`、`https://`） |
| `macro` | 多步串联 | `steps[]`（P1） |

`builtin` 的三个模块：`permdel`（隔壁安装器：`gui` / `install` / `uninstall` / `status` / `verify` /
`disclaimer` / `enginelog` / `checkupdate`）、`system`（12 个 Windows 组件，见 §4.4）、
`app`（本程序界面动作：`about` / `log` / `settings` / `checkupdate` / `newtool`）。

统一行为：默认隐藏黑窗口，输出异步读取（`ReadToEndAsync`，先等退出再读会在输出 >4KB 时父子互等），
超时强杀，退出码 + 输出尾部进日志。

## 7 `tools\*.json` 结构

```json
{
  "id": "permdel.gui",
  "tab": "rightmenu",
  "segment": 1,
  "order": 10,
  "name": "永久删除工具",
  "icon": "assets/icons/xxx.png",
  "kind": "builtin",
  "module": "permdel",
  "action": "gui",
  "options": "",
  "runAsAdmin": false,
  "confirm": false,
  "pinned": true,
  "danger": false,
  "placeholder": false,
  "hint": "P1"
}
```

- `placeholder: true` = 只做按钮不接功能（界面里画成灰色），`hint` 写提示里的阶段
- 内嵌：`tools\*.json`（`build.ps1` 以 `tools.<文件名>` 为资源名内嵌，编译后自检）
- 用户层：`%LOCALAPPDATA%\mxx1-toolbox\tools.json`，同 `id` 覆盖内置，升级不冲掉
- 编码 **UTF-8 无 BOM**；`%ProgramFiles%` 等占位符会展开
- 加载器只读 `tools` 数组：别的键（例如 `rightmenu.json` 里的 `_disabled`）当注释用，不会被当成按钮

## 10 红线

1. **编码**：`.cs` / `.ps1` **UTF-8 带 BOM**；`.vbs` 纯 ASCII；`.md` / `.yml` / `.json` 无 BOM。
   `build.ps1` 自动补 `.cs`/`.ps1` 的 BOM，`tools\Test-Encoding.ps1 -Fix` 兜底。
2. **排版**：一律 `TableLayoutPanel` / 排版函数，**绝不手写坐标**；标签绝不允许和按钮重叠。
3. **标题栏**：**主窗口** `MinimizeBox=true` + `MaximizeBox=false`（最小化要能用；那个灰掉的
   最大化方框是系统标准画法，用户 2026-10-06 拍板留着 —— 由来和实测见 §12.58）；**其它窗口**
   （关于 / 日志 / 设置 / 条款 / 结果窗口…）两个都 `false`。
4. **字形**：界面文字不用微软雅黑缺字形的 `✓ ⚠ →`；图标走 PNG 或程序内绘制。
5. **日志**：一律"最新的在最上面"，不给正序开关。
6. **危险动作**：二次确认 + 日志留痕 + 深红文字。
7. **不联网**：工具箱自身不联网，`checkupdate` 只读版本号。
8. **署名**：`mxx1` / `mxx1.cn` / GPL-3.0-or-later，字符串只从 `AboutForm` 取。
9. **不改隔壁仓库**：只在运行时调用它的 exe。
10. **推送前问用户**。

## 12 实现期间踩到并修掉的坑（别再踩）

1. **`Dock=Top` 的 `TableLayoutPanel` 会把多余宽度全塞给最后一列** —— 四列网格里
   每个第 4 个按钮都比同排宽 28px。修法：末尾加一个占 100% 的空列吃掉余量。
2. **`TableLayoutPanel` 的行默认是 AutoSize** —— 状态栏那一行按内容撑到 30px，而容器只有 24px，
   底栏按钮下边缘被裁 5px。修法：显式 `RowStyles.Add(Percent 100)`（同时按钮改成固定高 20px，
   因为 `AutoSize=true` 的按钮会自己长高）。
3. **列宽不能拍脑袋定**：按最长按钮名测量 + 留足图标余量。余量给 22px 时
   「关闭实时防护与篡改」渲染成「关闭实时防护与…」；给 36px 才够（还要加 `AutoEllipsis` 兜底）。
4. **GUI 子系统程序的 CLI 输出**：`Console.OutputEncoding` 在 stdout 是管道时改不动（setter 要真控制台），
   要么自己 `SetOut(UTF-8 writer)`；另外**不要**在 stdout 已被重定向时 `AttachConsole`，否则输出绕开管道，
   `$exe status | ...` 拿到空字符串。
5. **占位按钮的那 600ms 灰显**：界面测试要等它恢复再断言"按钮可用"，否则会把设计行为当成卡死。
6. **点击按钮时不许改文字**：原来运行中会显示 `名字…`，多出来的一个字符让"图标+文字"整组重新居中，
   每点一次图标就横跳一下（长名字还会溢出按钮被截断）。改成**换图标**（转圈，同样 16×16）+ 变灰，
   文字一动不动。回归检查 E05 直接读点击过程中的按钮文字，必须一字不变。
7. **状态栏文字必须放得下**：原来拼的是 `共 N 个按钮（本页 M） · 按钮名 · 完成：xxx 退出码 0`，
   实测 414px 塞进 392px 的标签 → 尾巴被截。改成短摘要 `N 个按钮 · 本页 M · 名字 · 完成`（最长 262px），
   完整内容进日志 + 标签悬停提示。检查：B06b（按钮文字不溢出）、D01d/E07（状态文字不溢出）。
8. **按钮高度必须按"字体 + 边框 + 内边距"算，不能只按字体算**：底栏按钮写死 20px 时装不下
   8.25pt 的一行字（用户："右下角按钮没正常显示、被挡住"）；改成 `MeasureText("国").Height + 6` = 22px
   后**还是差一行**（用户："底部按钮还是差一点的才显示全文字，主要是高度问题"）——
   因为 Flat 按钮除 1px 边框外还有约 3px 内边距，文字实际只能画在「高度 − 8」里，22px 只给到 14px。
   实测证据：底栏「检查更新」渲染出来只有 9 行墨迹，按钮墙上同字号的按钮有 10 行。
   最终公式 **`行高 + 8` = 24px（底栏 28px）**。检查：D01b（子控件落在容器内）、D01c（≥ 24px）、
   **D01e（数渲染出来的墨迹行数，必须和按钮墙一样多 —— 这条才是真正能抓住"被裁"的那个）**。
9. **WinForms 画图标的位置不等于按钮中心**：`FlatStyle=Flat` 的按钮把图片画在文字行框中心**往下 1px**，
   所以 16px 高的画布比按钮中心低 1px。实测（`PrintWindow` 抓像素，30px 的按钮）：
   图标墨迹在 9..23 行、中心 16.0，而按钮中心 14.5 —— 低 1.5px，同一按钮的文字中心恰好 14.5。
   修法：`IconFactory.Normalize()` 把**所有来源**（内嵌 PNG / 外部 PNG / 实时绘制 / 转圈图标）
   统一成 **16×15 画布**：首行整行透明时去掉那一行（等于把图案抬 1px），
   首行有墨迹的图改取 0..14 行（不切墨迹）。实测改完是 8..22、中心 15.0，误差 0.5px
   （整数画布下能做到的极限）。检查 B09（图标墨迹中心与按钮中心之差 ≤ 1px）。
   注意：`Padding` 挪不动这个偏差 —— 它把图标和文字**一起**挪（实测每 1px 底边距抬 1px），
   所以要动的是画布，不是内边距。
10. **PowerShell 数组的坑（本仓库踩过两次）**：`@(@('a','b'))` 传给函数会被解包成 `@('a','b')`，
    于是 `$p[0]` 取到的是**字符**而不是字符串 —— 用 `Replace` 批量改代码时会把整个文件改烂。
    脚本里要改文件就用两个平行数组 + 显式下标，或者干脆用编辑器逐个改。
11. **改完任何 `.ps1`/`.cs` 都要回头看 BOM**：编辑器（含各种打补丁工具）会静默吃掉 BOM，
    而 PowerShell 5.1 读无 BOM 的 `.ps1` 会按 GBK 解，中文注释直接变成语法错误
    （症状：`Missing using directive`、`Unexpected token` 之类莫名其妙的位置）。
    改完跑一次 `tools\Test-Encoding.ps1 -Fix`。
12. **PS 里逐像素扫图会慢到假死**：一个 `Get-Pixel` 函数按像素调用，几万次函数调用要几分钟，
    看起来像"卡住了"（实测被误判过一次）。要在 PS 里量像素就 `LockBits` 取一次 `byte[]`
    再纯数组循环（`tests\Test-Gui.ps1` 的 `Get-InkRows` 就是这么写的），或者干脆用 csc 编个小工具。
13. **灰度图标骗过了"图标判定"**（改灰色占位时踩到）：界面回归原来用"亮而饱和"（`max-min > 60 &&
    max > 140`）找图标，而置灰后的图标一点饱和度都没有 → 找不到图标 → `labelFrom` 退回 1 →
    把**灰色图标**当成文字算进去，墨迹行数从 10 行变成 15 行（D01e 立刻红）。
    修法：判据加一条"明显比底色暗"（`mx < bgMax - 45`），两种都认；同时把"图标上下居中"那条检查
    挪到**彩色图标**的按钮上（「右键增强」那个），别拿灰图标去量。
14. **单个 `PSCustomObject` 没有 `.Count`**：`function f { return @(单个对象) }` 会被 PowerShell 解包成
    一个对象（不是数组），而它的 `.Count` 返回**空**，于是 `$x.Count -gt 0` 恒为 False ——
    症状是"明明找到了弹窗，却判定成没找到"。调用处必须再包一层 `@(f ...)`。
    （和坑 10 是同一类：PowerShell 的数组/单值边界。界面回归的 F 组踩过。）
15. **WinForms 的 `ToolTip` 也是一个顶层窗口**：类名 `tooltips_class32`、标题为空。
    给网格按钮加了悬停提示以后，"除主窗口以外的可见窗口 = 弹窗"这个判据取到的第一个窗口
    就不是消息框了（F02/F03 直接红）。判"弹窗"要按窗口类：消息框是 **`#32770`**。
16. **界面测试不能依赖用户的 `settings.ini`**：用户把日志面板开着（`ShowLogPanel=1`）时，
    B08「默认不显示日志面板」会假红（一条"看起来像 bug"的失败）。现在界面回归一开头先写一份
    已知设置（浅色 / 单击 / 二次确认开 / 日志面板关），跑完在"现场复原"里按原样写回去。

17. **禁用的 Flat 按钮画出来的字比设定的颜色更深**：灰按钮改成 `Enabled=false` 以后，
    WinForms 用 `ControlPaint.DrawStringDisabled` 画标签，会在字下面描 1px 更深的影子 ——
    实测最暗像素从"我们设的纯灰 138"掉到 **77**，原来那条"最暗 ≥ 110"的检查立刻红了。
    修法：阈值按实测取 **≥ 60**，另外加一条**相对**判定（C01d：灰按钮必须比真按钮至少淡 30，
    真按钮实测 26）。教训：判定阈值要跟着**渲染现实**走，别跟着我们赋的值走。
18. **`BM_CLICK` 能绕过禁用状态**：界面回归是用 `PostMessage(BM_CLICK)` 点按钮的，而直接投递的消息
    不一定被"控件已禁用"挡住 —— 所以**不能**用"点一下没有反应"来证明"按钮点不动"。
    要证明禁用就读 `IsWindowEnabled`（E02/E03 就是这么做的）。
19. **把一排按钮收成一个时，先看还有没有别的东西只从这里进得去**：「右键增强」8 个按钮收敛成 1 个之后，
    **关于窗口（署名 / 许可证 / 打开设置目录）就没了唯一入口**，直到做 bin-tools 入口抽查时才发现。
    修法：底栏加第 5 个按钮「关于」。教训：删按钮 / 收页签时，先列一遍"它是不是某个功能的唯一入口"。
20. **加 / 删按钮要连带处理图标**：`tools\Make-Icons.ps1` 是从 exe 的 `list` 读清单再批量画的，
    所以顺序必须是 **build（清单进 exe）→ Make-Icons → 删掉不在清单里的孤儿 PNG → 再 build（图标嵌进去）**。
    漏删孤儿时 `build.ps1` 的自检会报"embedded icons 数对不上"。（删「Windows 激活」时踩了一次。）
21. **"相对路径按 exe 目录解析"会把 URI 也当成文件路径**（用户实际点出来的）：
    `bin-tools\` 那条改成"相对路径先按工具箱目录找"之后，`ms-settings:storagesense` 这种
    **URI 也属于"不是绝对路径"**，于是被拼成 `<工具箱目录>\ms-settings:storagesense`，
    用户点「存储感知设置」看到的是 **"打开失败：系统找不到指定的文件"**。
    修法：`AppPaths.Resolve` 先认 URI —— 冒号前是协议名、且整串既不含 `\` 也不含 `/` → 原样返回；
    凡是"给相对路径加前缀"的逻辑都要先过这一关。检查：命令行 `run storage-sense --dry` 必须打出
    `target=ms-settings:storagesense`（而不是拼过前缀的路径）。
22. **自己写 JSON 的字段拼接助手别把逗号放在第一个字段前面**（用户实际遇到的）：
    `UserTools.ToJson` 原来每个字段都拼 `", "`，于是第一个字段写成 `{ , "id": ... }` ——
    人看着只是多一个逗号，**工具箱自己的解析器直接判非法**，报"JSON 对象缺少键（位置 109）"，
    症状是"图形化新建的按钮当场消失、重开也读不回来"。修法：加一个 `First()` 助手，首个字段不加逗号。
    教训：手写序列化器必须有**回读自检**（界面回归 C13：图形化建一个按钮 → 用 `list` 读回来），
    光看写出来的文件"像不像 JSON"是发现不了的。
23. **`DllImport` 忘了 `ExactSpelling`，把整个界面回归拖死**（2026-10-04 卡了一次，用户看着屏幕说"卡在
    点击新建按钮弹出的窗口了"）：给 `SetText` 写的是 `CharSet = CharSet.Unicode` + 方法名
    `SendMessageStringW` → 运行时先去查 **`SendMessageTextWW`**（Unicode 会把 `W` 加到**入口点**上，
    不只是方法名），查不到就抛 `EntryPointNotFoundException`。后果不是"一条检查红"，而是：
    输入框一直是空的 → 「创建按钮」点不动 → **模态窗口一直开着** → 主窗口保持禁用状态 →
    后面每一组"点主窗口"的检查全部连带失败，测试看着像卡死。修法：`EntryPoint = "SendMessageW",
    ExactSpelling = true`。**两个教训**：① 跨进程写控件的检查必须**回读断言**（`[TBGui]::Text`），
    写不进去就当场判死；② 开过模态窗口的测试，**每条分支的出口都要关掉它**（`Close-StrayDialogs`
    在 C 组收尾还加了一条 C16 专门盯"有没有残留模态窗口"）。
24. **测试被打断 = 用户的按钮清单和设置被留在"暂停"状态**：界面回归/命令行回归为了数按钮数，
    会把用户自己的 `tools.json` 改名成 `.paused-by-*`，跑完再放回来；一旦中途被 Ctrl+C / 卡死 /
    沙箱杀进程，这个"放回来"就永远不会执行 —— 用户看到的是"我建的按钮凭空没了"。
    修法：**开工先自愈**（发现 `.paused-by-*` 存在而正式文件不存在，先搬回去），
    `settings.ini` 也留一份 `.before-test` 备份，收尾成功才删。
    教训：测试对用户真实数据的"临时占用"必须有**崩溃后可恢复**的设计，不能只靠 finally。
25. **`path` 展开环境变量了，`args` 却没有**（用户实际点出来的："hosts 修改没有正常打开"）：
    「hosts 修改」是 `path=%SystemRoot%\notepad.exe` + `args=%SystemRoot%\System32\drivers\etc\hosts`，
    `Resolve/Expand` 只作用在 `path` 上，参数被**原样**丢给进程 —— 记事本收到字面量
    `%SystemRoot%\...`，于是弹"找不到文件"（或问你要不要新建一个叫这个名字的文件）。
    修法：`Launcher.ExpandArgs()`，只展开 `%变量%`，开关/引号/多参数原样保留。
    教训：**一个"路径字段"的修法要同时问一遍"参数里的路径呢"**；回归 D06 把每个 `kind=exe`
    按钮的 `--dry` 都跑一遍，`command=` 里不许残留 `%变量%`。
    同一轮还发现日志行把 cmd 脚本显示成 `cmd -Command "..."`（cmd 只有 `/c`，实际执行是对的）——
    显示的字符串错了会把人往错方向带，所以显示代码也要跟着真命令一起改。
26. **模态窗口开着的时候，拖放事件仍然会落到主窗口**（用户实际遇到的："点击新建按钮后拖入程序图标后
    会打开一个新的新建按钮弹出的窗口，应该只弹一个的"）：`AllowDrop` 挂在主窗口 / 内容面板 / 网格上，
    而**模态对话框只挡住鼠标键盘，挡不住 OLE 拖放** —— 拖进来的文件照样触发网格的 `OnDragDrop`，
    于是又 `ShowDialog` 出一个「新建按钮」窗口。
    修法两层：① `MainForm._userDialogOpen` 守卫，已经开着一个就不再开（并给一句状态提示）；
    ② **让对话框自己接拖放**（`NewToolForm.EnableDrop` 递归给每个子控件 `AllowDrop = true`，
    因为拖放落在光标底下的那个控件上），拖进来直接填当前窗口。
    教训：给窗口加拖放时，要问一句"它弹出模态子窗口的时候，拖放会去哪儿"。
27. **拖进来的快捷方式（.lnk）要解析成它指向的真程序**（用户："拖入快捷方式图标程序会失败修复一下
    （直接指向目标地址）"）：原来 `.lnk` 走 `else` 分支被当成 exe，按钮里存的是**快捷方式本身的路径** ——
    快捷方式一挪走、一改名，按钮就废。修法：`DroppedFile.ResolveShortcut()` 用 `WScript.Shell`
    晚绑定（csc 没有 COM 引用，靠反射调 `CreateShortcut`）取 `TargetPath / Arguments / WorkingDirectory`；
    取不到（比如指向「此电脑」这种 shell 文件夹的快捷方式）就退回 `kind: open` 让系统当双击打开。
    另外 `Launcher` 在 `kind: exe` 启动前也补了一次解析 —— 老版本建出来的按钮照样能跑。
    测试：拖拽手势是 OLE 拖放、没法在测试里合成，所以把**决策**做成命令行 `draft <路径>`
    （只打印会变成什么按钮，不写文件），回归 G01–G06 盯它。
28. **"打开官方界面"这类按钮，盲开就是静默失灵**（做安全类那一批时发现的，影响 5 个按钮 + 2 个旧按钮）：
    用户的机器是**精简版 Windows** —— 我按常规写法准备的入口，一半在这台机器上根本不存在：

    | 入口 | 这台机器上的结果 |
    | --- | --- |
    | `ms-settings:windowsdefender` | 能打开"设置"，但 `SettingsPageVisibility` 策略把 `windowsdefender` **这一页藏了** |
    | `shell:appsFolder\…SecHealthUI` | Windows 安全中心 App **没装**（`Get-AppxPackage` 查不到），explorer 回退成了打开「文档」 |
    | `wf.msc`（高级防火墙） | **不在**（`mmc.exe` 打开的是空控制台，看着像成功） |
    | `netsh advfirewall` | **不存在**（`advfirewall` 上下文整个没了） |
    | `control.exe /name Microsoft.WindowsFirewall` / `firewall.cpl` | 退出码 0、**一个窗口都没有** |
    | `control.exe /name Microsoft.BitLockerDriveEncryption` | 同上（现有的 BitLocker 按钮一直是死的） |
    | `Get-NetFirewallProfile` / `Get-NetAdapter` | NetSecurity / NetAdapter 模块**都不在** |
    | `manage-bde -status` | Provider load failure（WMI 提供程序也没了） |
    | `UserAccountControlSettings.exe` / `desk.cpl` / `services.msc` / `gpedit.msc` | **能开**（这才是正常的那些） |

    修法：这类按钮**一律先探测再打开**（`Test-Path` / `Get-Command` / `Get-AppxPackage`），
    探测不到就给一句"这台系统里 XX 已被移除，没有能打开的界面"，而不是"点了没反应"。
    探测可用性时**别用 `Get-NetAdapter` / `Get-NetFirewallProfile` 当判据**（它们本身可能没装），
    用 WMI（`Get-CimInstance Win32_NetworkAdapter`）+ 文件存在性更稳。
    教训：**"官方界面"不是常量**，除了系统版本（Win10/Win11）还要考虑"组件被精简掉了"。
29. **回读校验分不清"我写的"和"本来就是"**（写「关闭按流量计费」时踩到）：
    脚本先试着写 `DefaultMediaCost`，失败后**读回**看是不是 1 —— 而它默认就是 1，
    于是失败被当成成功，弹出"已设为不计费"的假消息。修法：**以"写入是否抛异常"为准**
    （`try { … } catch { $ok = $false }`），读回只用来在消息里显示当前值。
    教训：**用状态值判断"操作成功"时，先问一句"这个值有没有可能本来就是这样"**；
    比较可靠的是"操作前后有没有变化"，或者干脆看操作本身有没有报错。
    同一个键还有个坑：`DefaultMediaCost` 的 ACL 只给 `SYSTEM` / `Wcmsvc` / `TrustedInstaller` 写权限，
    **管理员也只有读**（提权也写不进，逐连接的 `Cost` 值写了也不改变计费类型）——
    所以"按流量计费"在第三方程序里基本只能打开设置页让用户自己点。
### 12.30 悬停说明不能直接甩命令行（用户报的「鼠标悬停的说明没有做好」）

`TipFor` 原来是「按钮名 · `Launcher.DescribeCommand`」：对 `kind=script` 且带 `inline` 的按钮，
那就是把整段 PowerShell 摊在一行里（「一键清理垃圾」700 多字、顶出屏幕），而**真正写给人看的
`hint` 反而不显示**。现在第一行按钮名、第二行 `hint`、再按需补「会弹确认框 / 会弹 UAC 窗口」，
命令只在 100 字以内（人能看懂：路径、URI、短开关行）时才附上。

顺带三件事：① `ToolTip.AutoPopDelay` 默认只有 5 秒（长句子读不完）、`ShowAlways` 默认 false
（窗口一失焦就再也不弹），都调过来了；② 「系统工具」那 12 个按钮的 `hint` 原来是搜索关键词
（"硬件 驱动 msc"），当说明太糙，全改成一句人话；③ 新增 CLI 命令 `tip [id]` 打印界面塞给
`ToolTip` 的那条原字符串，测试才能不动鼠标就盯住它（GUI 那边还有 `B10/B11` 真悬停一次）。

### 12.31 PowerShell 的逗号比 `+` 优先级高（`@($a+'x', $b+'y')` 会拼成一个字符串）

`@($d + '\User Data', $up + '\User Data')` 里**逗号（数组构造）比算术 `+` 结合得更紧**，
于是整串被算成一个字符串、循环只跑一次、`Test-Path` 永远 False —— 「清理浏览器缓存」因此
"看起来在工作、其实一个目录都没命中"。每个元素加括号才正确。

### 12.32 单引号字符串不解释反引号

`'`r|`n'` 在 PowerShell 里是字面量「反引号 r 竖线 反引号 n」，不是正则的 CR/LF。
`-split` 要真正的正则转义：写 `'\r|\n'`（JSON 里是 `'\\r|\\n'`）。踩在「系统文件修复 SFC」上。

### 12.33 往 `tools\*.json` 末尾追加条目，别忘了给上一条补逗号

运行时遇到坏 JSON 会把**整个文件**丢掉（只在日志里留一条警告）：那一页的按钮会全部消失。
`tools\Test-InlineSyntax.ps1` 现在把"清单能不能解析"当失败报出来（这个坑是加它的时候现踩的）。

### 12.34 WinForms 的 ToolTip 窗口类名带前缀

实际类名是 `WindowsForms10.tooltips_class32.app.0.34f5582_r6_ad1`：精确匹配
`tooltips_class32` **一个都找不到**，于是"没有出现提示"这个结论是错的（绕了一轮才用 `EnumWindows`
把本进程的窗口全列出来看清）。判据要用 `IndexOf("tooltips_class32")`。同理：ToolTip 只认真实
光标位置（`Cursor.Position`），合成的 `WM_MOUSEMOVE` 不会让它弹出来 —— 测试里要 `SetCursorPos`
真把光标移过去，跑完再放回原处。

### 12.35 `Get-ChildControls` 给的是屏幕坐标

界面上"顶部那一排页签"不能写 `Top -lt 32`：那是屏幕 Y（几百）。要拿主窗口的上边当参照，
而且 `GetWindowRect` 给的是整窗（含标题栏）—— 客户区在标题栏下面约 30px。

### 12.36 被禁用的控件收不到鼠标消息（所以灰按钮没有悬停提示）

`Enabled = false` 的按钮不响应 `WM_MOUSEMOVE`，WinForms 也就不会弹提示。灰按钮的解释因此写在
底栏（"灰色 N 个没接功能"）。真想让灰按钮也有悬停说明，得改成"其实能点但点下去什么都不做"，
那是另一套语义（当前实现保持"禁用"）。

### 12.37 需要管理员的"进程内动作"没法自己提权

隐私开关的注册表写入必须在**本进程**里做（要读回核对），所以写 HKLM 时不能像外部 exe 那样
`Verb=runas` 直接提权。做法：`run <id> --admin` 把自己再起一遍（子进程提升权限），结果是 winexe
没有控制台，于是写进 `last-elevated-result.txt`，父进程用 1 秒定时器盯几秒、读出来弹结果窗口。

### 12.38 测试脚本里"函数定义在调用之后" = 脚本当场死掉（而且不收拾现场）

PowerShell 是**边解析边执行**：函数只有执行到定义那一行才存在。`Switch-Tab` 定义在第 735 行、
第一次调用却在第 566 行 → `CommandNotFoundException`，脚本在第 7 项检查处终止，
**收尾那段"把用户自己的 tools.json 放回去"根本没跑**，用户下次打开会以为"我建的按钮没了"
（2026-10-04 真发生了一次：`tools.json.paused-by-gui-test` 留在磁盘上，正式文件没了）。

两条修法一起上，缺一不可：

1. 函数定义**一律放在第一次调用之前**（本仓库的 `Test-Gui.ps1` 把 `Switch-Tab` 挪到了探针辅助区）；
2. 收尾逻辑抽成 `Restore-UserLayer` 函数，并在脚本开头挂一个**脚本级 `trap`**：
   任何未捕获的终止错误都先复原设置 / 用户 `tools.json` / 杀掉自己拉起来的界面进程，再 `exit 1`。
   进程用 `$script:Procs` 记着（`Start-Gui` 里 `Add`），**只杀自己起的**，绝不碰用户自己开着的窗口。

> 顺带一条纪律：两套测试都会把用户层"暂停"，所以**测试中途尽量不要做别的写操作**；
> 真被中断了，下次开工有自愈（发现 `.paused-by-*` 在而正式文件不在就先搬回去）。

### 12.39 往 `tools\*.json` 追加条目时的一个多余逗号，会让**整份清单**被丢掉

`Json.cs` 是严格解析：多一个逗号 → 这个文件整个解析失败 → `list` 少掉一整页按钮
（实测 105 → 73，日志里一行 `tools.common.json: JSON 里出现无法识别的字符 ']'（位置 14090）`）。
更坑的是**校验工具会骗你**：PS 7 的 `ConvertFrom-Json` 对尾随逗号很宽容，用它验证是"通过"的。

纪律：改完清单用**严格**解析器验一遍（`[System.Text.Json.JsonDocument]::Parse(...)`），
或者直接 `bin\Mxx1Toolbox.exe list --tab <页签>` 数一遍按钮。

### 12.40 改 `settings.ini` 之前必须先关掉正在跑的那个窗口

窗口关闭时会把**它当前停留的页签**写回 `settings.ini`（`LastTab`，"记住上次停留的页签"功能）。
测试里先写设置、再关窗口 = 被覆盖 → 下一个实例开在别的页签上，后面那一组检查全假红
（2026-10-04：深色组的 G03/G05 就是这么红的，深色实例开在了 F 组最后停的「清理优化」上）。

### 12.41 "固定宽度"要真固定：宽度得粘住，超长名字改用省略号

用户原话：「主界面宽度固定一下，反正按钮不会跟随变化而自适应」。只把窗口设成不可 AutoSize 是不够的：
`ComputeCellWidth()` 是按**最长按钮名**量的，用户加一个 32 个字的按钮，下次开机列宽从 147 撑到 170、
窗口 628 → 720 —— 那还是"跟着内容变"。两条一起做才算固定：

1. **宽度粘住**：第一次量出来的宽度立刻写进 `settings.ini` 的 `WindowWidth`（不是只在关闭时写，
   否则被强杀的进程就丢了），之后开机都用它；用户拖过窗口再以拖出来的尺寸为准；
2. **列宽夹一道**：`ClampCellWidthToWindow()` 把列宽限制在 `(固定宽度 − 24) / 4` 以内，
   名字装不下就用省略号（`AutoEllipsis`，悬停提示里是全名），既不会撑宽窗口，也不会把同排挤出去。

判据在 `Test-Gui.ps1` H 组：H03 换页签窗口尺寸一动不动、H04 加个 32 字长的按钮宽度还是 628、
H05 那一页按钮数还对。

### 12.42 `StartPosition = CenterParent` 对非模态窗口无效 —— 窗口会掉到屏幕左上角

用户报的：「点击激活状态为什么会弹到左上角窗口」。原因不是坐标写错，而是**语义**：
`FormStartPosition.CenterParent` **只在用 `ShowDialog()` 打开的模态窗口上生效**；
用 `Show(owner)` 打开的非模态窗口完全不认它，Windows 就按自己的默认位置放 —— 实际就是屏幕左上角。
结果窗口、日志窗口、常用链接都是非模态的（要能一边看结果一边继续点按钮），所以全中招。

修法：`src\WindowPlacement.cs` 的 `ShowCentered(form, owner)` —— 对着 owner 的客户区居中，
再夹进那块屏幕的 `WorkingArea`（别顶到任务栏下面 / 屏幕外），**同时开着好几个窗口时每个往下错 28px**
（完全叠在一起的话，用户会以为只开了一个）。用法就是拿它替换 `f.Show(this)`。

判断"有没有落回左上角"不能只看"窗口弹出来了"：回归 `E04b` 比的是**结果窗口与主窗口的重叠比例**，
要求 ≥ 50%（居中时实测 ~89%，左上角时接近 0）。
### 12.43 界面回归的"悬停"检查是真动鼠标 —— 别的窗口盖住按钮就会假红

`B10`/`B11` 要验证悬停说明，做法是 `SetCursorPos` 把系统鼠标挪到按钮中间，再读 `ToolTip` 窗口的文字。
这条链路上任何一环被环境打断都会假红：**用户自己开着另一个工具箱实例**（他那份窗口正好压在测试实例上）、
用户此刻在动鼠标、前台被别的程序抢走。2026-10-04 真发生过一次：用户 20:16 双击打开了
`bin\Mxx1Toolbox.exe`（窗口在 63,244），测试实例居中在 646,267，两个窗口叠了一角，第一列按钮的悬停在
4 秒里一次都没成功，B10/B11 报"没找到说明" —— 看起来像功能坏了，其实是环境。

处理（两条都做了）：
1. **测试实例自己挑位置**：写 `settings.ini` 之前先枚举屏幕上已经开着的工具箱窗口，从"左上 / 右上 /
   左下 / 右下 / 居中"几个候选里挑第一个**不和它们相交**的角落（`WindowX`/`WindowY`），
   于是测试永远不会和用户自己开着的窗口打架；
2. **悬停重试 3 次**，并且失败时把 `[TBGui]::WindowAt(x,y)`（鼠标底下那个窗口的 pid / 类 / 标题）
   和 `Foreground()` 打进失败信息 —— 下次一眼就能看出"鼠标下面是别人的窗口"还是"真的没弹说明"。

### 12.44 `edit` 类工具会静默吃掉 `.ps1` 的 BOM —— 改完必须先修再跑测试

2026-10-04 真踩：给 `tests\Test-Cli.ps1` 追加 M 组（一百多行）之后直接跑回归，结果满屏
`Unexpected token '}' in expression or statement`，而且报错位置全在**别的函数**上，中文全成了
`涓枃杈撳嚭` 这种乱码。原因不是语法写错了，而是**补丁工具把文件的 BOM 吃掉了**：没有 BOM 的
`.ps1` 会被 PowerShell 5.1 按 GBK 解码，UTF-8 的中文注释和字符串当场变成语法垃圾。

规矩：**每次用 `edit` / 写文件的方式改完任何 `.cs` / `.ps1`，先跑 `tools\Test-Encoding.ps1 -Fix`，
再 `build.ps1`，最后才是测试。** 顺序颠倒的话，你看到的不是"我改错了"，而是一屏毫不相干的报错。
`build.ps1` 自己也会给 `src\*.cs` / `tests\*.ps1` / `tools\*.ps1` 补 BOM，所以"改完直接 build
再跑测试"也能救回来 —— 但别指望它，手动补一次只要一秒。（判断方法：文件头三个字节是
`EF BB BF` 才算有 BOM。）

### 12.45 Restart Manager 的三个坑（"谁占着这个文件"）

`src\FileLock.cs` 用系统自带的 `RstrtMgr.dll` 回答"谁占着这个文件"。实测（本机 + 一个独立探测）
踩到三个反直觉的地方：

1. **目录路径绝对不能传进去**：`RmRegisterResources` 收下目录不报错，但 `RmGetList` 会回
   `ERROR_ACCESS_DENIED(5)`，而且**污染整批** —— 目录和"明明锁着的文件"一起传，连那个文件也
   不报了（全有或全无）。所以文件夹要先自己枚举成文件列表。**枚举必须往下走**（v1.5.1 改的）：
   原来只取第一层，于是"文件夹第一层全是子文件夹"（右键一个项目文件夹，占用它的是子文件夹里
   那个 Word 文档）就一个文件都登记不到，直接放弃 —— 用户 2026-10-04 报的「没扫描到占用文件」
   就是这个。现在按层（BFS）往下扫：深度 ≤4、文件数 ≤400、跳过软链接 / 联接点、整次扫描
   最多 4 秒。代价：文件夹被某个程序当成"当前工作目录"这种占用 RM 查不到，这一条由
   `FileLock.SelfCheck` 兜底（用 `CreateFile` + `share=0` + `FILE_FLAG_BACKUP_SEMANTICS` 独占
   打开那个目录，回 `ERROR_SHARING_VIOLATION(32)` 就说明"确实有人占着它，只是报不出名字"）。
2. **一个坏路径能毁掉整批**：含非法字符的路径，或者 `kernel32.dll` / `user32.dll` 这类
   "人人都在用的已知 DLL"，会让整批回 0 结果 + 错误码（这次还撞到文档里没写的
   `ERROR_INVALID_HANDLE(6)`）。所以整批失败要**二分劈开重查**：劈到单个文件为止，
   单个还失败就记下来跳过（不拖累别的）。比"逐个文件重试"省得多 —— 400 个文件里有 1 个坏的，
   只多花十几次查询（`QueryResilient`）。
2b. **一批登记 400 个文件，RM 只说"哪几个进程"，不说是哪个文件**。所以先把整批问一次
   （实测 60 个文件一批只要 10ms，和查 1 个一样）判"有没有"，有命中再**逐个文件**问一遍
   （≈11ms/个，上限 60 个）把"占着哪个文件"落下来 —— 这行信息对"右键文件夹"最关键。
3. **它报的是"友好显示名"，不是路径**：`strAppName` 是 `Windows PowerShell` / `Windows 资源管理器`
   / `Windows Event Log` 这种名字，拿不到完整 exe 路径（要自己按 PID 反查进程名）；
   `svchost.exe` 里挂着的几个服务会返回**同一个 PID 好几行**，所以按 PID 去重（"结束进程"本来就是
   按 PID 干的，列四遍同名同号只是噪音）。

顺带两条：非管理员照样能查出**别人的**进程（用 `runas /trustlevel:0x20000` 的真·非管理员令牌验过），
只有查自己无权打开的文件（`SAM` / `System.evtx`）才回 5；"共享读"也算占用（3 个进程同时以
只读打开同一文件 → 报 3 个），对"文件删不掉"这个场景反而更对。

### 12.46 `& <exe>` 对 GUI 子系统程序**不等待** —— 在命令行里读它的输出会读串

2026-10-04 真踩：排查"RM 到底查不查得到占用"时写了 `& bin\Mxx1Toolbox.exe rightmenu unlock
--query-only <文件>`，结果 PowerShell **不等待** winexe（它按 GUI 程序处理），`$LASTEXITCODE`
是空的、`$o = & $exe ...` 拿到的是 `$null`，四次调用的输出还全挤在最后一起冒出来 —— 我一度
以为"RM 查不到占用"，其实是把**上一次调用的输出**当成了这一次的结论。

规矩：**工具箱是 `/target:winexe`，命令行里一律 `Start-Process -Wait` + `-RedirectStandardOutput`
读输出**（`tests\Test-Cli.ps1` 的 `Invoke-Exe` 就是这么写的）。要直接 `&` 跑，就只能看它往
继承的控制台里吐的东西，别指望顺序和退出码。

### 12.47 GDI+ 的 `Image.FromStream` 要那个流活到图片用完

`src\MenuIcons.cs` 把内嵌 PNG 转成 `.ico` 时踩了一下：`using (MemoryStream ms = ...) { img =
Image.FromStream(ms); }` 之后再拿 `img` 画东西，会得到"参数无效"这种没头没脑的 GDI+ 异常
（GDI+ 是**惰性解码**的，流关掉了它才去读）。修法：把 `using` 套在外层，让流活到图用完
（`using (ms) using (img = Image.FromStream(ms)) { ... }`）。
另外 .ico 别指望 PNG-in-ICO：这里自己拼 32 位 DIB（`BITMAPINFOHEADER` + 自下而上的 BGRA +
全 0 的 AND 掩码），16/20/24/32 四个尺寸，Vista 之后所有 Windows 都认。

### 12.48 `assets\app.ico` 不存在时，`/win32icon` 那行会**静默失效**

`build.ps1` 里写的是 `if (Test-Path $icon) { $cscArgs += ('/win32icon:' + $icon) }` —— 文件不在就
悄悄跳过，编出来的 exe 一点提示都没有，只是"没图标"。用户 2026-10-04 报「编译好的
Mxx1Toolbox.exe 没有图标」就是这个：**这一行等于从来没生效过**（v1.5.1 查右键菜单图标时就已经
发现"这个 exe 自己没有图标资源"，当时只绕开了菜单那一侧）。
现在：文件不在时 `Write-Warning` 喊一嗓子，文件在时打印 `icon : <路径> (字节数)`；
回归由 Test-Cli 的 A14–A17 盯着（ico 文件 → 格式与尺寸数 → `/win32icon` 那行 → **exe 上按像素验**）。

### 12.49 WinForms 的窗口图标**不等于** exe 的资源图标

同一个坑的另一半：`/win32icon` 只把图标写进 exe 的**资源**（资源管理器 / 快捷方式看的是它），
而 WinForms 的窗口不设 `Form.Icon` 时画的是它自带的"空白窗体"图标 —— 标题栏和任务栏依旧是
没图标的样子。所以 `src\AppIcon.cs` + `Mxx1Form`：`LoadImage(hInstance, "#32512", IMAGE_ICON, cx, cy)`
按窗口要的尺寸取那一档（csc 写的就是资源组 **32512**），`Form.Icon` 给**大图**（WinForms 自己重发
图标时两边都用它）、随后补一次 `ICON_SMALL`。判据也只能按像素：`.NET` 那个默认图标**一点纯白都
没有**，我们的图标是蓝底 + 四个纯白方块 —— Test-Gui 的 A04b / N16 就是这么判的。

### 12.50 窗口高度别按"行数"拍公式（内容会换行）

「解除文件占用」的小窗口原来是 `210 + 行数 × 20`（最多 470）—— 只算了列表，**上面那几行文字一行
都没算**。结果：行数少时偏高；**"没查到占用"**时正文有八九行（自查结论 + 能不能删 + 为什么 +
四条可能原因），下面被切掉一半（用户 2026-10-04 报「窗口高度没有做自适应高度」）。
修法（`UnlockForm.UpdateSize`）：文字用 `TextRenderer.MeasureText` 按**标签自己的
`MaximumSize.Width`** 量（高 DPI 下 WinForms 会把 MaximumSize 一起放大，用常量量出来的行数偏多），
列表用 `ListViewItem.Bounds`（Details 视图里第一行的 `Top` = 列头高度、`Height` = 行高）量，
相加后夹进屏幕工作区；高度变了还要**按原来的中心点重新摆一次**，否则窗口只会往下长。
回归：Test-Gui N14/N15/N17/N18 —— 判据是"每个可见控件都完整落在客户区 + 底部空白 ≤ 40px"，
用**屏幕坐标**比，所以 125% / 150% DPI 下同样成立。

### 12.51 路径比较前必须归一化 8.3 短名（CI 上抓到的一个真漏报）

**现象**：CI 上 `M14e`（「它自己在运行」）永远红：`run=0`，可进程明明活着、镜像明明在目标文件夹里。
**根因**：GitHub runner 的临时目录是 **8.3 短名**（`RUNNER~1` 那种写法），而
`QueryFullProcessImageName` 报回来的镜像路径是**长名** —— `ProbeRunners` 里那句
`img.StartsWith(dir + "\", OrdinalIgnoreCase)` 于是永远不成立。
（句柄那条路还有另一半：`GetFinalPathNameByHandle` 报的路径带 `\\?\` 设备前缀。）
**修法**（`src\FileLock.cs`）：目标路径过一遍 `GetLongPathName`（不存在的路径原样返回，安全），
镜像路径去掉 `\\?\` / `\\?\UNC\` 前缀 —— 两边都变成规范长名再比。
**教训**：**任何"把两个来源的路径用字符串比"的地方，都要先问一句"它俩可能是短名 / 长名 / `\\?\` 三种写法吗"**。
这类 bug 在开发机上永远复现不了（本机 8.3 生成是关的，`RUNNER~1` 那种名字根本不存在）。
回归：`M14e`（外加它自己的**夹具自检**：那个进程的镜像必须真在目标文件夹里，不在就跳过并写明原因）。

### 12.52 `Copy-Item` 拷目录不带 `-Recurse` = 只建一个空目录

**现象**：用户 2026-10-05 解压 Release 里的源码包，报「bin-tools 里面只有 PermanentDeleteSetup.exe
进压缩包了，memreduct 没有进」。翻 zip 时还发现 `assets\icons\` 在包里是个**空目录** ——
一百多张按钮图标一张都没进去（"从包里的源码编译出来的 exe 没有按钮图标"，而 zip 表面上是完整的）。

**根因**：打包那几行写的是 `Copy-Item (Join-Path $root 'assets\*') (Join-Path $stage 'assets') -Force`，
**没有 `-Recurse`**。通配符展开出来的 `assets\icons` 是个目录，`Copy-Item` 在这种情况下
**只创建目录、不拷里面的文件**，而且不报错、不给警告 —— 看着就像"拷过了"。
`bin-tools\` 更直接：原来只硬编码拷隔壁那一个安装器，目录里的别的东西连看都没看。

**修法**（`tools\Make-Package.ps1`，v1.5.3 发布后）：① 要打进包的东西**逐条列出来**
（`Add-PackItem` / `Add-PackTree` 枚举文件），不依赖通配符的隐式行为；② 打完包**回读 zip 逐个核对**，
少一个就让打包失败（和 `build.ps1` 查内嵌资源一个套路）；③ 打包单独成脚本，测试可以直接调
（命令行回归 **P 组**），不用为了测打包把整个工程重编一遍。

**教训**：**"打包"这种一次性的批处理，一定要有一句"打完自己回读核对"**。
凡是"看一眼输出像是成功了"的步骤，都在等着一个没人会发现的空目录。

### 12.53 保存设置时，别把"同意记录"一起写回旧值（用户报「每次打开都弹条款确认」）

**现象**：用户 2026-10-05 报「使用条款确认 首次运行，每次打开都弹出，不正常」。
日志里看得清清楚楚：`08:42:25 已同意当前这版条款 指纹=f4c21191…` → `08:42:35 还没有同意当前这版条款`
（十秒之后又要求确认一次）。

**根因**：主窗口的 `_settings` 是在**构造函数**里 `Settings.Load()` 的，而条款确认门在 `OnLoad` 里 ——
也就是说这份快照是**同意之前**的（`AgreedDisclaimer` 空）。`Consent.Accept()` 自己 `Load` 一份新的
写进 `settings.ini`（指纹确实落盘了），但用户关窗口时 `OnFormClosed` 又拿那份**旧快照** `Save()` 一遍，
把刚记下的同意覆盖成空 → 下次打开又弹，永远弹。

**修法**（两层）：
- `Settings.Save()` 里**同意记录只认磁盘上的那份**：没被 `ConsentTouched` 标记过，就先 `Load()` 一份
  把 `AgreedDisclaimer` / `AgreedAt` 合并回来（只有 `Consent.Accept` / `Consent.Reset` 会置这个标记）。
- `MainForm.OnLoad` 确认通过之后顺手把快照刷成磁盘现值（读者不用再想"这份对象是哪一刻的"）。

**实测**（发布前后对照，同一份 `settings.ini`）：
`同意→agreed  关窗口→required`（旧） vs `同意→agreed  关窗口→agreed`（新）。

**教训**：**"进程里这份对象是哪一刻加载的"要跟着字段一起想**。凡是"另有一条更权威的写入路径"的字段
（同意记录、注册表原值、安装状态…），`Save()` 就不该无条件拿内存值盖盘，
要么别放在这个对象里，要么保存前合并。回归：界面 `I10b`（关窗口后记录还在）/ `I10c`（重开不再弹）——
原来的 `I09` 是在窗口**还开着**的时候查的，所以这个 bug 从测试里溜过去了。

### 12.54 扫描跑在界面线程上 = 窗口"死了"（实测卡 6.5 秒，用户问「有没有优化空间」）

**怎么发现的**：用户 2026-10-05 问「工具箱里面的解除文件占用功能还有没有优化的空间？」。
翻代码时看到 `UnlockForm.RefreshLockers()` 里是 `_report = FileLock.Scan(_paths);` —— 直接在
`Shown` 事件里（= 界面线程）同步查。于是写了个探针量它：起一个 `rightmenu unlock "<文件夹>"`，
一边每 50ms 用 `SendMessageTimeout(WM_NULL, SMTO_ABORTIFHUNG)` 问一次"你还处理消息吗"。

**实测**（400 个文件的文件夹、窗口 184ms 出现）：

```
     184 ms  窗口出现
     612 ms  卡住=True      ← 从这里开始，一条消息都不回
    7093 ms  卡住=False     ← 6.5 秒后才活过来
```

这 6.5 秒里窗口拖不动、关不掉、任务栏会写「（无响应）」。
别的文件夹量出来是 0.2 秒（小文件夹）～ 15 秒（系统目录那一片）。

**时间花在哪**（在 `local\` 里编了个带计时的探针，直接复用 `FileLock.cs`，逐段量）：

| 阶段 | 耗时 |
| --- | --- |
| 收集文件 + 自查 | 59 ms |
| **系统查询（`RmGetList`）** | **5940 ms** |
| 定位是哪个文件被占着 | 653 ms |
| 扫运行中的进程 / 窗口 | 80 ms |

也就是说 **90% 的时间在系统接口里**，工具自己的代码只占 0.8 秒。又量了两件事：

- **拆小批次没用**：400 个一批 5620ms，50 个一批查 8 次 5461ms —— 每条路径都要系统花同样多的钱，
  所以"更快"没法从这里抠；
- **同样的文件换个位置快 25 倍**：`.git\objects` 那 400 个文件 6102ms，复制到另一个文件夹 234ms；
  400 个空 txt 106ms。**慢不慢取决于系统对那批路径的心情**，代码里预判不了。

**修法**：扫描放**后台线程**，查完 `BeginInvoke` 回界面刷新。三件事一起做：
① 状态行每半秒改一次秒数（`System.Windows.Forms.Timer` 跑在界面线程上，**它还在动就说明界面没被堵住**）；
② 这期间三个按钮禁用（`UpdateButtons()`），查完恢复 —— 结论：**按钮"在"不等于"能点"**，
  界面回归里点按钮之前必须等它 `Enabled`（N09 真踩过：点了禁用按钮，然后假红成"没弹出确认框"）；
③ 窗口随时可以关（背景线程是 `IsBackground`，关掉进程就退）。

**回归**：界面 `N20` —— 起一个 400 个文件 + 一个真占用的文件夹，每 20ms 问一次 WM_NULL，
量**最长一次没人应的时长**，要求 < 500ms；`N20b` 是夹具自检（那一轮真的在扫、真的出了结论，
不然 N20 等于没测）。**修好后实测 0ms**（原来是整个扫描的时长）。

**教训**：**"这一步要几秒"就不能放在界面线程上**，哪怕它"平时只有 0.2 秒"——
用户的文件夹有多大、系统那一刻有多慢，都不是你能决定的。判据也别用"窗口还在不在"：
窗口一直在，只是它不回消息了。

### 12.55 「前 60 个文件」这种定位法在大文件夹里基本等于没定位（改二分）

**怎么发现的**：量 12.54 的时候顺手试了一发 —— 造一个 400 个文件的文件夹，把**第 200 个**文件锁住，
再查：

```
hits=1 lockers=1
note=查到了占用的程序，但没定位到是文件夹里哪个文件（可以直接结束它们试试）。
```

**根因**：`Attribute()` 是拿文件夹里**前 60 个**文件（`MaxAttributeFiles = 60`）挨着问一遍。
被占的文件排在第 61 个之后，就永远问不到，只能退回"没定位到具体文件"那句 ——
而"指名是哪个文件被占着"正是 v1.5.1 专门做出来的东西（§14.11），文件夹一大就失效了。

**修法**：**二分定位**（`FileLock.Bisect`）。整批已经问出"有人占着"了，就把它劈成两半各问一次，
哪一半有人占着就继续往下劈，一路劈到单个文件。这招能成立的前提是 Restart Manager
**全有或全无**（一批里只要有一个被占着，这一批就报"有人占着"）——同一批里没人占着就整批吃掉，
一次查询省掉一半文件。

**实测**：400 个文件、占用在第 200 个上 → 原来 60 次查询都定位不到，现在**9 层约 18 次查询**就指名了。
而且**更快**：每问一次系统约 12ms，60 次约 0.7 秒 → 18 次约 0.2 秒。
查询次数有预算（`MaxAttributeQueries = 64`，和原来 60 个文件的花费相当）：被占的文件很多时
（System32 那种）二分树会变大，超了预算就停下并如实说"还有 N 个文件没定位"。

**教训**：**"挨着问前 N 个"和"我先问一半"是两个完全不同的东西** —— 前者是碰运气，
后者在你已经知道"这批里有人占着"之后是**确定性**的，而且更快。

### 12.56 系统托盘气泡"显示与否由系统说了算"，而且位置钉在右下角（用户报「气泡没有正常弹出」）

**怎么发现的**：用户 2026-10-06 拿到 v1.5.4 的上一版之后实测，原话是
**「气泡没有正常弹出，而且弹出的位置要跟随鼠标」**。

**根因**：提示走的是 `NotifyIcon.ShowBalloonTip` —— 那是**系统**画的气泡：
① 能不能看见由系统的通知设置说了算（这台是精简版 Windows，通知平台被裁过；Win10 / Win11 关掉
「通知」或开着专注助手时同样看不到），于是用户在**自己机器上**看到的可能是"点了什么都没发生"；
② 它长在**托盘旁边（右下角）**，位置由系统定，离用户正看着的鼠标很远 —— 一个"做完了没有"的反馈
落在屏幕另一个角落，等于没有；③ 它还得先在托盘里短暂冒一个图标（`Shell_NotifyIcon` 的规矩）。

**修法**：**自己画一张卡片**（`src\Balloon.cs` 的 `NoticeForm`）—— 不经过系统的通知平台，
一定画得出来；位置自己算，就在鼠标旁边。四条规矩都是硬要求：

| 规矩 | 怎么做的 | 不改的理由 |
| --- | --- | --- |
| 不抢焦点 | `ShowWithoutActivation` + `WS_EX_NOACTIVATE` | 正在打字时它弹出来，字照样打进原来那个窗口 |
| 不占任务栏 / 不进 Alt+Tab | `ShowInTaskbar = false` + `WS_EX_TOOLWINDOW` | 它是提示，不是窗口 |
| 跟着鼠标 | 60ms 的 `Timer` 读 `Cursor.Position`，挪够 `FollowSlack = 8` 像素才动 | 免得抖；用户要的就是"位置跟着鼠标" |
| 自己消失 / 点一下也关 | `Timer`（默认 6s，`--notify=<毫秒>` 可定）+ `OnMouseDown` → `Close()` | 不许赖着不走，也不许挡在那儿关不掉 |

**位置规则**（`NoticeForm.PlaceAt`）：默认放在鼠标**右下** 18 / 22 像素；那一侧放不下就翻到另一侧
（**翻过就记住**，鼠标压在临界线上时不会来回跳）；最后无论如何都夹进**鼠标所在那块屏幕**的
工作区（多显示器 / 鼠标贴着屏幕边也不会跑出去）。实测（探针拿 `GetCursorPos` + `GetWindowRect`
对着量，屏幕 1920×1040 工作区）：

```
鼠标 700,300    → 卡片 718,322    dx=18   dy=22      ← 默认右下
鼠标 1200,500   → 卡片 1218,522   dx=18   dy=22
鼠标 400,700    → 卡片 418,722    dx=18   dy=22
鼠标 1880,1020  → 卡片 1603,940   dx=-277 dy=-80     ← 右下放不下，翻到左上
```

**教训**：**"让系统替你显示一个提示"= 把"能不能看见"交给用户的系统设置**。凡是用户必须看到的
反馈（"我到底做没做"），要么画在自己的窗口里，要么就别指望它 —— 这次连**位置**都是系统说了算的，
而用户的要求恰恰是"位置要跟着我的鼠标"。另外 **"有窗口"不等于"看得见"**：回归 N21d 抓
`PrintWindow` 的像素数墨迹，才叫验证过"卡片上有字"。

### 12.57 「进程名黑名单」拦不住系统进程 —— 看**归属**才拦得住（CI 上抓到的真事故）

**怎么发现的**：不是自己发现的，是 **CI 抓的**。v1.5.4 推上去之后 GitHub 的 runner 上
**M34 红了**，而且红得很难看：

```
[FAIL] M34 不许动系统关键进程：被几个 svchost 服务占着的日志文件一动没动
       (auto=killed killed=2 占用者 3→1)
```

本机跑这一条一直是 `killed=0`、占用者 4→4（四条 svchost 全都认出来了）—— 也就是说
「一键解除」在**别的机器上真的去结束了系统服务**，而且那台机器上我们正好是管理员，
「结束失败」这最后一层保险也没兜住。

**根因**：这条路的底线原来是一张**进程名黑名单**（`CriticalNames`：svchost / lsass / wininit…），
名字来自 `Process.GetProcessById(pid).ProcessName`。而**权限不够时这个名字读不出来**
（`Win32Exception: 拒绝访问`），代码就退回 `RmGetProcessInfo` 报的**友好名** ——
那是"Windows Event Log"这种**服务名**，黑名单一条都对不上：

```csharp
f.Exe = ExeNameOf(pid);                       // 读不到 → 空
if (f.Exe.Length == 0) { f.Exe = AppName; }   // 于是 Exe = "Windows Event Log"
...
return !NameIn(CriticalNames, bare);          // "windows event log" 不在名单里 → 允许结束 ☠️
```

**教训（这条最值钱）**：**"名字"是别人给的、随时可能读不到；"归属"是系统给的、读不到就拒绝。**
黑名单/白名单这种按名字判断的做法，只要名字来源可能失败，就等于没有名单 —— 而且失败时
恰好是在**权限受限的机器**上，那里往往正是系统进程最多的地方。

**修法**（`FileLock.AutoUnlockTarget` 现在是「归属 + 来源 + 名字」三层，任何一层不确定就拒绝）：

| 拒绝条件 | 字段 | 怎么判断 |
| --- | --- | --- |
| 不是**当前用户**的进程（SYSTEM / 别的账户 / TrustedInstaller） | `NotMine` | 开进程令牌 → `TokenUser` 的 SID 和当前进程比（`FileLock.IsOwnedByCurrentUser`）；**读不到就当成"不是自己的"** |
| 系统报的类型就是「服务」 | `IsService` | `RM_PROCESS_INFO.ApplicationType == RmService` |
| 连进程名都读不出来 | `NameUnread` | `ExeNameOf(pid)` 空 —— 这时 `Exe` 里装的是友好名，禁止名单对它无效 |
| 系统关键进程 / `pid ≤ 4` / explorer / 工具箱自己 / 「窗口里开着它」 | `Protected` 等 | 原来那一套（保留） |

窗口那条路（有确认框、用户自己勾）**一个字都没改** —— 这条规矩只加在**没有确认框**的自动路上。

**本机实测**（改完当场验的，两种情形都要对）：

```
$ Mxx1Toolbox.exe rightmenu unlock --auto --quiet <System32\winevt\Logs\System.evtx>
auto=locked  killed=0  targets=                     ← 一个都没挑中（原来在 CI 上会挑中 2 个）

$ Mxx1Toolbox.exe rightmenu unlock --auto --quiet <被我自己开的 powershell 独占的文件>
auto=killed  killed=2  targets=powershell.exe       ← 自己的程序照结束（连子进程）
（再查：lockers=0 candelete=yes）
```

**回归**：M34（真靶子：系统事件日志文件，本机和 CI 都要 `killed=0`，失败信息里带上
`targets=` —— 一眼看出"挑中了谁"）；**M39** 是**源码级看门狗**：断言 `AutoUnlockTarget`
里那三条拒绝还在（真造一个"系统服务占着文件"的现场要管理员 + 计划任务，造不出来只能 Skip，
那等于没测；M34 在 CI 上已经把这条路真跑过了）。

### 12.58 「只给最小化」的窗口，系统会画一个灰掉的最大化方框（这次的取舍是留着它）

**背景**：用户 2026-10-06「**给工具箱右上角添加一个最小化，目前很影响体验，只有关闭的情况下**」。
而 §10 第 3 条红线原来写的正是 `MinimizeBox=false` + `MaximizeBox=false` —— 那条红线的由来**就是**
那个灰方块（原来的理由写着"标题栏多一个灰掉的最大化方框，点了没反应"）。所以这不只是加一行的事，
是一次**取舍**。

**先量，再挑**：写了个小探针（`%TEMP%\mxx1-cap\Probe.cs`，五个变体各截一张标题栏，
再用 `WM_GETTITLEBARINFOEX` 打每个按钮的矩形和状态）在这台机器上实测：

| 变体 | 标题栏画出来什么 | `TITLEBARINFOEX` 报的状态 |
| --- | --- | --- |
| `Min=false Max=false`（改动前的工具箱） | 只有 ✕ | min/max 都 `0x8000`（这一格不存在） |
| **`Min=true Max=false`（这次选的）** | **— ＋ 灰方块 ＋ ✕** | min=`0x0`（可用）、max=**`0x1`（unavailable）** |
| `Min=true Max=true` | — ＋ 亮方块 ＋ ✕ | 两个都 `0x0` |

结论：**"只给最小化"必然带一个灰掉、点不动的最大化方框** —— 这不是 WinForms 的毛病，是系统对
`有 WS_MINIMIZEBOX / 无 WS_MAXIMIZEBOX` 这种窗口的标准画法（`xxxDrawCaption` 从 Win95 起就是这规矩）。
想同时做到"有最小化"+"标题栏没有灰方块"，只有两条路：**让最大化真能用**，或者**自绘标题栏**。

**为什么两条路都没走**（把对比截给用户看之后，他拍板"**只要最小化，那个灰方块留着**"）：

- **让最大化真能用**：按钮墙是**固定 4 列、列宽不随窗口变**（§2 第 17 条，用户自己定的规矩），
  最大化之后墙挤在左上角，右边和下方一大片空白；而且 `WndProc` 里 `WM_EXITSIZEMOVE` 那段和
  `RememberGeometry` 会把铺满屏幕的尺寸写进 `settings.ini`，**把用户记住的窗口大小冲掉**。
  真要做，得连"最大化时按窗口宽度重排列数"一起做 —— 那是另一个功能，不是加一个按钮。
- **自绘标题栏**（`FormBorderStyle.None` + 自己画 "— ✕"）：要自己接管拖动、八向缩放、贴边、
  DWM 阴影、DPI 与 Win7 那一路 —— 为了藏一个灰方块不值当。

**落地**：`src\MainForm.cs` 里一处 `MinimizeBox = true`（旁边写明了"**别为了藏灰方块把
`MaximizeBox` 改成 true**"，以及为什么）；其余 10 个窗口仍然"两个都 false"。

**回归**：`A03` 原来断言的是"标题栏**没有**最小化方框"，现在反过来断言**有**，另外补了
**A03b/A03c** —— 真发一次 `WM_SYSCOMMAND / SC_MINIMIZE`（`IsIconic` 必须为真），再 `SW_RESTORE`
叫回来，**位置和尺寸必须一字不差**。只看样式位不算数：位对了但窗口下不去、或者还原之后跑偏，
都是真出事过的那一类。

## 13 外部工具放哪：`bin-tools\` 工具目录（①③ 层**已实现**）

**背景**：工具箱现在会调一个外部程序（隔壁的 `PermanentDeleteSetup.exe`），以后还会加别的
（解压、卸载、查硬盘…）。用户 2026-10-04 的意见是"**应该建一个子文件夹，毕竟后续还得加其他 exe 工具**"。
这一节就是照这个思路排的方案：**一个约定好的工具目录 + 统一的查找顺序**，内嵌只是一层可选兜底。

### 13.1 三层结构（可以只做第一层，也可以叠加）

| 层 | 做什么 | 代价 | 收益 |
| --- | --- | --- | --- |
| **① 工具目录（已实现：用户选的名字是 `bin-tools`）** | 工具箱目录下建 **`bin-tools\`**，外部工具按原文件名丢进去；查找顺序里加这一档；`build.ps1 -Package` → `tools\Make-Package.ps1` **把整个 `bin-tools\` 拷进发布包**（含用户自己放的工具，缓存 / 临时文件除外，打完回读 zip 逐个核对）；设置窗口加「打开工具目录」，找不到工具时的提示里带上这个路径 | 小（`Launcher` 加一档查找 + 打包脚本 + 一个入口按钮） | 加工具 = 丢文件；工具箱目录结构清楚；杀软无感 |
| **② 内嵌兜底（可选）** | `build.ps1` 把 `bin-tools\` 里的 exe 也 `/resource:` 进去；运行时若磁盘上找不到，就释放到 `%LOCALAPPDATA%\mxx1-toolbox\bin-tools\`（比长度/哈希，变了才重写）再启动 | 中（释放逻辑 + 版本比对 + 测试） | 真·单文件：只拷 `Mxx1Toolbox.exe` 也能用 |
| **③ 工具清单自动扫（v1.5.3 已实现）** | `bin-tools\<工具名>\tool.json` 描述它的按钮（名字/图标/参数），工具箱启动时扫一遍自动生成按钮，不用改 `tools\*.json` | 大（新格式 + 扫描 + 冲突处理 + 测试） | 加一个工具 = 丢一个文件夹，按钮自己长出来（见 §13.7） |

### 13.2 目录长这样

```
萌新工具箱\
  Mxx1Toolbox.exe            ← 主程序（按钮清单与图标都内嵌在里面）
  bin-tools\                 ← 外部工具全放这里（① 层，已实现）
    说明.txt                 ← 这个文件夹是干什么的（第一次打开界面时自动放进来）
    PermanentDeleteSetup.exe ← 想「自带」这个工具就复制进来（可选）
    （以后）Everything.exe / GeekUninstaller.exe / ...
  README.md / LICENSE        ← 分发 zip 里带着
```

**这个文件夹空着是正常的**（用户 2026-10-04 问过「bin-tools 里面为什么是空的？」）：工具箱不依赖
里面的东西，「永久删除工具」按钮会一路找到上一层相邻仓库的 `permanent-delete-menu\bin\`。
所以第一次打开界面时会自动建好这个目录并放一份 **`说明.txt`**（`AppPaths.EnsurePayloadDir()`，
只在缺文件时写、不覆盖用户改过的），把"往里放什么、为什么空着也能用、放进去的东西优先级更高
（所以隔壁重新编译后要换掉旧副本）"写清楚 —— 空文件夹看着像坏了。

**为什么叫 `bin-tools` 而不是 `tools`**：仓库里的 `tools\` 已经是"按钮清单 JSON + 构建脚本"的意思，
而 `build.ps1 -Package` 会把仓库的 `tools\*.json` 拷到发布目录根部 —— 发布目录里再来一个
`tools\`，就会出现"同一个文件夹里既有 JSON 又有 exe"的混乱。名字也可以叫 `apps` / `bin-tools`，
**只要不与 `tools` 撞名**。

**找不到工具时把路径写进提示**（"没找到 PermanentDeleteSetup.exe —— 请把 exe 放进
`<工具箱目录>\bin-tools\`，或在「设置」里指定路径"），并且设置窗口/关于窗口给一个
**「打开工具目录」**按钮（点一下没有就自动建好并打开），这样"加工具"这件事不说自明。

### 13.3 查找顺序（最终建议）

1. 「设置」里用户指定的完整路径（`settings.ini` 的 `PermanentDeleteExe`）—— 永远最高，方便调试；
2. **工具箱目录 `bin-tools\<文件名>`**（① 层的主角，已实现）；
3. （② 层，没做）内嵌释放出来的 `%LOCALAPPDATA%\mxx1-toolbox\bin-tools\<文件名>`（② 层，只在 1、2 都没有时用；
   释放目录必须**固定**，不能放 `%TEMP%` —— 隔壁装进右键菜单后，引擎脚本虽然在
   `%LOCALAPPDATA%\PermanentDelete\`，但用户以后还会再打开这个 exe 去卸载/修复，临时目录被清就找不到了）；
4. 开发场景兜底：向上三层找 `permanent-delete-menu\bin\PermanentDeleteSetup.exe`（现在就有，留着方便开发）；
5. `%LOCALAPPDATA%\PermanentDelete\`（隔壁自己可能会放一份）。

### 13.4 相对路径（**已实现**）

`kind: "exe"` 的 `path` 以前只做环境变量展开，**相对路径按进程当前目录解析**（不可靠）。
现在 `AppPaths.Resolve()` 规定：**相对路径先找工具箱目录、再找 `bin-tools\`**，
所以清单里写 `"path": "PermanentDeleteSetup.exe"` 或 `"path": "bin-tools\Xxx.exe"` 都能用
（`icon` 字段和 `open` 的 target 走同一条路）。回归检查 F04 就是拿一个临时按钮验证这件事的。

**URI 必须先认出来再谈相对路径**（坑 21，用户实际踩到）：`ms-settings:storagesense` 这类 URI
同样"不是绝对路径"，一开始被拼上了工具箱目录，于是点「存储感知设置」报"系统找不到指定的文件"。
现在 `Resolve()` 的第一条就是 **URI 守卫**：冒号前是协议名（`colon > 0`）且整串既不含 `\` 也不含 `/`
→ **原样返回**，不加任何前缀。

### 13.5 各方案的取舍（原问题：要不要一起打包进 exe）

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A 保持现状 | 不打包，运行时四处找 | 零维护、隔壁升级立刻生效、杀软无感 | 单独拷 `Mxx1Toolbox.exe` 到别的机器时那个按钮用不了 |
| B 内嵌 | `/resource:` 进 exe，首次点击释放到固定目录 | 真·单文件，拷贝即用 | exe 里套 exe，个别杀软会多看一眼；体积 +135 KB |
| C 工具目录 | 就是上面的 ① 层（`bin-tools\` 子文件夹） | 最简单、杀软最友好、以后加工具最省事 | "单文件"变成"一个文件夹" |


用户 2026-10-04 选了 **C / ① 工具目录**，名字定为 **`bin-tools`**，**已经实现**：
查找顺序（含工具目录档位）、`build.ps1 -Package` 自动拷入、「打开工具目录」入口、相对路径按工具目录解析。
**B（内嵌成单文件）还没做** —— 等用户说"我只想拷一个 exe"再加，查找顺序天然支持共存。

### 13.6 用户自己往里放一个工具（Mem Reduct 那次定下来的流程）

用户 2026-10-04 问「把 Mem Reduct 放进 `bin-tools` 的正确流程是什么？怎么保证不会被清除？」，
答案分两半：

**放法**：整个文件夹拷进 `<工具箱目录>\bin-tools\<工具名>\`（按架构挑子目录，`64\` 是 x64）——
**别只拷 exe**，便携版通常还带语言文件 / 便携标记（Mem Reduct = `memreduct.lng` + `portable.dat`，
内容 `#PORTABLE#`，缺了会变英文或改去写注册表）；按钮写在**用户层** `tools.json` 里，
`path` / `workdir` / `icon` 都写**相对路径**（`memreduct\memreduct.exe`），靠 `Resolve()` 解析；
图标要真图标就用 `ExtractIconEx` 的 small（16×16）那一张另存 PNG 放在同一个文件夹
（`Normalize()` 只做 16×16 画布、不缩放，所以原生 16px 那张最清楚）。验证不用点按钮：
`run <id> --dry` 看 `target=` 指到 `bin-tools` 且 `exists=yes`。

**"不会被清除"的边界（如实写在文档里，不吹）**：`build.ps1` / `build.ps1 -Package` /
`Make-Icons.ps1` / `Make-AppIcon.ps1` / 启动时的 `EnsurePayloadDir()` 都不碰这个目录；
`tests\Test-Cli.ps1` 的 F02/F03 只操作**它自己拷进去的那一份** `PermanentDeleteSetup.exe`
（目录里本来就有就跳过拷贝，收尾也**绝不删别人的文件**），并且只在目录**不存在**时才会建了又删。
唯一的真风险是 **`bin/` 不入 Git**（`.gitignore` 一行 `bin/`）：手删 `bin\`、换机器 / 重新 clone、
把 exe 挪走（`bin-tools\` 跟着 exe 走）都会丢 —— 所以原始安装包留着，或者再放一份到
`%LOCALAPPDATA%\mxx1-toolbox\bin-tools\`（备用工具目录，查找顺序里排在 exe 旁边那份之后）。

**发布包里带不带这些工具**（2026-10-05 用户报「memreduct 没有进压缩包」之后定的）：
`build.ps1 -Package` → `tools\Make-Package.ps1` **会把 exe 旁边这个 `bin-tools\` 整个复制进发布包**，
所以在哪台机器上打包，包里带的就是那台机器上的工具（缓存 / 临时文件 / `说明.txt` 除外，
`说明.txt` 由工具箱第一次打开界面时自己写一份最新的）。**"里面有什么"由这台机器的工具目录决定，
不是由仓库决定** —— 想让别人也拿到，就把工具放进 `bin-tools\` 再打包（见 §12.52 的教训）。

### 13.7 工具文件夹自动长按钮（v1.5.3 已实现 —— 用户问「bin-tools 里面的工具是不是应该自动加载一个按钮？」）

**答案：应该，而且已经做了。** 实现是 `src\ToolFolders.cs`（约 300 行，纯只读），
由 `src\ToolRegistry.cs` 在**用户层之后、内置清单之前**接一层扫描结果。

**扫谁**：`AppPaths.PayloadDir`（exe 旁边那个 `bin-tools\`）和 `AppPaths.UserPayloadDir`
（`%LOCALAPPDATA%\mxx1-toolbox\bin-tools\` 备用目录）下的**一级子文件夹**。
子文件夹里再套一层目录（`64\`、`x64\`、`bin\` 之类）也认 —— `FindExe` 会在里面找。

**怎么决定按钮长什么样**：

| 文件夹里有什么 | 结果 |
| --- | --- |
| `tool.json`（推荐） | 按它来：`id`（默认 `auto.<文件夹名>`）/ `name` / `tab` / `segment` / `segmentName` / `order` / `kind` / `path` / `args` / `workdir` / `icon` / `runAsAdmin` / `hint` 都能写，缺的用默认值 |
| 没有 `tool.json`，里面只有**一个** exe | 就用它（`kind=exe`，`workdir` = 那个文件夹） |
| 没有 `tool.json`，里面有**多个** exe | 只在其中**有一个和文件夹同名**时用它；否则**这个文件夹不生成按钮**，日志里写明原因 —— **不猜** |
| 里面一个 exe 都没有 | 跳过（不生成按钮），也写日志 |

**默认值**（用户什么都不写的时候）：`tab=mine`（「我的工具」页签）、`segment=2`、
`segmentName=bin-tools 里的工具（自动加载）`、`order=40`、`name` = 文件夹名、
`id=auto.<文件夹名>`、`workdir` = 文件夹、`icon` = 文件夹里的 PNG（有就用；没有就走内置图标）。

**四条底线**：

1. **只读**。扫描不改任何文件、不写 `tools.json`（`ToolItem.AutoLayer = true`，右键菜单里不能编辑 / 删除，
   要改就改文件夹里的 `tool.json` 或整个文件夹）。
2. **绝不覆盖**已有 id。和内置清单或用户 `tools.json` 撞 id 时**自动按钮让位**，日志写
   `按钮 id「X」已经存在（内置清单或用户 tools.json），这一条自动按钮被跳过`。用户想手工接管某个工具，
   只要在 `tools.json` 里写一条同 id 的按钮就行。
3. **坏清单只坏自己**：某个文件夹的 `tool.json` 读不动 / 字段非法 → 只跳过那一条并写日志，
   别的按钮照常（不会像"整份 `tools\*.json` 语法错"那样全丢）。
4. **不刷新界面也能确认**：`status` 里 `autoButtons=N` + 每个自动按钮一行
   `autoButton=<页签>\t<id>\t<来源>`，`run <id> --dry` 能看到它指向哪个 exe（`icon=` 那行只在
   PNG 真在磁盘上时打印）。

**用户怎么用**：把工具文件夹整个拷进 `bin-tools\`，按 **F5**（或重启工具箱）就多一个按钮；
想改名字 / 图标 / 参数，在文件夹里放一个 `tool.json`（编码 **UTF-8 无 BOM**）；
`bin-tools\说明.txt`（第一次打开界面时自动生成）里写的就是这几条。

## 14 「右键增强」v1.5.0 / v1.5.1 / v1.5.2：把工具箱的两件事装进 Windows 右键菜单

> 2026-10-04 用户拍板：① 两项都**装进 Windows 右键菜单**（不是在工具箱里再做一个窗口）；
> ② 「解除文件占用」不做"先选文件"的窗口 —— 文件由资源管理器选中；③ 「最近使用」最多留 30 个。
> 设计正本就是本节，实现是 `src\RightMenu.cs`（注册表）+ `src\FileLock.cs`（查占用）+ `src\UnlockForm.cs`
> （结果窗口）+ `src\MenuIcons.cs`（菜单图标）+ `tools\rightmenu.json`（10 个按钮）。
>
> **v1.5.1 修的就是用户当天报的两个问题**：「菜单里的两项没有图标」和「右键一个文件夹，没扫描到
> 占用文件」。根因、修法与实测见 **§14.11**。
>
> **v1.5.4（未发布）加了第三项**：「一键解除占用」—— 用户 2026-10-05 要的"不弹出窗口的版本"。
> 原来那个窗口版一个字节都没改，这是**另外一条**入口（`rightmenu unlock --auto`），见 **§14.14**。

### 14.1 装什么、装在哪（只用 HKCU）

**不要管理员、不装 shell 扩展 DLL、不起服务、不加开机启动。** 微软文档
（[用 ExtendedSubCommandsKey 建级联菜单](https://learn.microsoft.com/zh-tw/windows/win32/shell/how-to-create-cascading-menus-with-the-extendedsubcommandskey-registry-entry)）
写着：`HKEY_CLASSES_ROOT` 是 `HKEY_CURRENT_USER` 和 `HKEY_LOCAL_MACHINE` 的合并，所以在
`HKCU\Software\Classes` 下注册子动词**不需要提升权限**。

| 出现在哪 | 键（都在 `HKCU\Software\Classes` 下） |
| --- | --- |
| 任意文件 | `*\shell\Mxx1Unlock` / `*\shell\Mxx1AutoUnlock` / `*\shell\Mxx1Common` |
| 文件夹 | `Directory\shell\Mxx1Unlock` / `Directory\shell\Mxx1AutoUnlock` / `…\Mxx1Common` |
| 文件夹里的空白处（= 当前文件夹） | `Directory\Background\shell\Mxx1Unlock` / `…\Mxx1AutoUnlock` / `…\Mxx1Common` |
| 桌面空白处 | `DesktopBackground\Shell\Mxx1Unlock` / `…\Mxx1AutoUnlock` / `…\Mxx1Common` |

（v1.5.4 之前是两项；第三项和第一项的结构一模一样，只是标题、图标和命令里多一个 `--auto`。）

```reg
; 「解除文件占用」= 普通 verb
[HKCU\Software\Classes\*\shell\Mxx1Unlock]
"MUIVerb"="解除文件占用"
"Icon"="C:\Users\<你>\AppData\Local\mxx1-toolbox\rightmenu-icons\rightmenu.unlock.on.<指纹>.ico"
"MultiSelectModel"="Player"
@=""                                   ; 默认值必须留空（否则和 MUIVerb 打架）
[HKCU\Software\Classes\*\shell\Mxx1Unlock\command]
@="\"<工具箱 exe>\" rightmenu unlock \"%1\""

; 「一键解除占用」= 同样是普通 verb，只是命令多一个 --auto（不弹窗口那条路）
[HKCU\Software\Classes\*\shell\Mxx1AutoUnlock]
"MUIVerb"="一键解除占用"
"Icon"="…\rightmenu-icons\rightmenu.auto.on.<指纹>.ico"
"MultiSelectModel"="Player"
@=""
[HKCU\Software\Classes\*\shell\Mxx1AutoUnlock\command]
@="\"<工具箱 exe>\" rightmenu unlock --auto \"%1\""

; 「常用功能」= 级联子菜单：父键只指向共用的子项键
[HKCU\Software\Classes\*\shell\Mxx1Common]
"MUIVerb"="常用功能"
"Icon"="…\rightmenu-icons\rightmenu.common.on.<指纹>.ico"
"MultiSelectModel"="Player"
"ExtendedSubCommandsKey"="Mxx1Toolbox.Common"
@=""

; 子项只写一份，四个位置共用（重建菜单只写这一个地方）
[HKCU\Software\Classes\Mxx1Toolbox.Common\shell\01]
"MUIVerb"="计算器"
"Icon"="…\rightmenu-icons\calc.<指纹>.ico"
[HKCU\Software\Classes\Mxx1Toolbox.Common\shell\01\command]
@="\"<工具箱 exe>\" run calc"
```

**占位符按位置写**（v1.5.1 修的 bug）：

| 位置 | 占位符 | 为什么 |
| --- | --- | --- |
| 任意文件 / 文件夹 | `%1` | 资源管理器把选中的路径填进来 |
| **文件夹里的空白处** | **`%V`** | 这两个位置资源管理器**不替换 `%1`**，会把字面量 `%1` 原样当路径传进来 —— 结果就是"路径不存在"、查不到任何占用 |
| **桌面空白处** | **`%V`** | 同上 |

- `Icon` 必须是**绝对路径**，而且只能是"带图标资源的 exe / dll"或者一个 **`.ico` 文件**
  （**指 `.png` 是无效的** —— Windows 不认）。工具箱的图标是 114 个内嵌 PNG，所以装菜单时由
  `src\MenuIcons.cs` 现场转成 `.ico` 写到 `%LOCALAPPDATA%\mxx1-toolbox\rightmenu-icons\`
  （文件名带源图指纹，图标改了装一次就换新；转出来是 16/20/24/32 四个尺寸，125% / 150% DPI
  也挑得到合适的那张）。**注意：v1.5.0 这里写的是 exe 路径，而那个 exe 从来没有 `/win32icon`
  （`assets\app.ico` 不存在）→ 菜单里就是一片空白**，这就是用户报的"没有图标"。
- `Icon` 指向的路径**每次装 / 重建时都要读回核对**（`WriteIconValue`：写失败或指不到文件就
  把这个值删掉，绝不留一个空白图标位）。
- `CommandFlags=0x20`（ECF_SEPARATORBEFORE）用来在「最近用过」和固定三项之间画一条分隔线。

### 14.2 「解除文件占用」点了以后发生什么

1. 资源管理器调 `"<工具箱 exe>" rightmenu unlock "<选中的路径>"`（多选就是多个路径）。这是 winexe，
   没有黑窗口。**v1.5.4 起这一步是异步的**：窗口先出现，扫描在后台线程上跑，状态行每半秒改一次
   秒数（"正在检查谁占着它……（已经 N 秒）"），查完再刷列表 —— 所以窗口全程可拖可关
   （原因与实测见 §12.54；「一键解除占用」那条路连窗口都没有，见 §14.14）。
2. 工具箱用 **Windows 自带的 Restart Manager**（`RstrtMgr.dll`：`RmStartSession` →
   `RmRegisterResources` → `RmGetList`）问系统"谁占着这个文件"。**不用装 handle.exe、不要管理员**。
   这一层是**三层做法**（v1.5.1 定型，根因见 §14.11）：
   - **扫**：右键的是文件就查它；是**文件夹就按层往下扫 4 层、最多 400 个文件**（跳过软链接 /
     联接点，整次扫描最多 4 秒）—— "占着文件的程序"多半在子文件夹里（Office / PDF 文档）；
   - **查**：整批先问一次（实测 60 个文件一批只要 10ms，和查 1 个一样）判"有没有"；整批失败就
     **二分劈开重查**，把系统不认的那个路径隔离出去；有命中再**逐个文件**问一遍（≈11ms/个、
     上限 60 个）落定"是哪个文件被占着"；
   - **自查**：不管查没查到，都自己试着**独占打开**一次那个路径（见第 4 条）。
3. 弹一个**小窗口**（`UnlockForm`，弹完即走，和主界面无关）：

```
┌─ 解除文件占用 ─────────────────────────────────────┐
│ D:\项目\年报资料                                    │
│ 查到 1 个程序占着它（文件夹里扫了 12 个文件）：       │
│ ┌───────────────────────────────────────────────┐ │
│ │ 程序           PID   占着的文件     说明         │ │
│ │ [x] WINWORD.EXE 8124 Q3报告.docx  主窗口        │ │
│ └───────────────────────────────────────────────┘ │
│ [结束选中的进程] [重新检查] [复制路径] [关闭]        │
│ 提示：勾上要结束的程序…「占着的文件」那一列说明它    │
│       占着文件夹里的哪一个文件。                    │
└───────────────────────────────────────────────────┘
```

4. **查不到人时不许只说"查不到"**，必须给确定结论（`FileLock.SelfCheck` 自己去独占打开一次）：

   | 自查结果 | 窗口里说的话 | 意思 |
   | --- | --- | --- |
   | 能独占打开它 | 「我自己能独占打开它 —— 现在真的没有程序占着它」 | 真没人在用；删不掉多半是权限 / 只读 / 内核态扫描 |
   | 独占打开被拒（共享冲突 `0x80070020`；目录回 `err=32`） | 「确实有程序占着它，但报不出是哪个程序」 | 有占用，只是这个接口看不到（对方权限更高 / 别的用户），窗口给三条可操作建议 |
   | 权限被拒（`0x80070005`） | 「不是被占用，是权限或只读属性拦住了」 | 根因不是占用，别去杀进程 |
   | 路径不存在 | 「这个路径不存在 —— 资源管理器没把路径传过来…背景位置要用 `%V`」 | 旧版菜单装在"空白处"位置上就会这样 |

5. 「结束选中的进程」走 `ConfirmForm` 二次确认后 `Process.Kill`，逐个报结果；**同一个 PID 只结束
   一次**（它可能占着好几个文件、在列表里出现好几行）；结束不了（权限不够 / 进程已退出）逐条写明
   原因。**绝不谎报"已解除"。**

**底线（代码里写死 + 回归盯着）**

| 底线 | 为什么 |
| --- | --- |
| 只结束**用户勾选**的进程，一个都不多杀 | 右键菜单是误点高发区 |
| `explorer.exe` 默认**不勾**（结束它 = 桌面重启） | 用户会以为电脑坏了 |
| 系统关键进程（`System` / `csrss` / `winlogon` / `services` / `lsass` / `wininit` / `smss`）**列出来但禁止勾选**并写明原因 | 杀了会蓝屏 / 掉登录会话 |
| **不做句柄级强杀**（关句柄那种内核动作） | 有蓝屏风险，不做 |
| 不碰隔壁「永久删除」装的 verb | 两个工具各卸各的 |

### 14.3 「常用功能」子菜单 = 「常用」页的镜像

- 内容 = **置顶的按钮**（`pinned.txt`）+ **最近用过的按钮**（`recent.txt`，**上限 30**）+ 固定三项
  「打开工具箱 / 运行日志 / 设置」。

  「最近使用 · N 个（最多 30 个）」跟着变。

### 14.6 实测结论（动手前先验的，2026-10-04）

| 待验的 | 结论 |
| --- | --- |
| Restart Manager 能不能指出占用进程 | **能**。自己锁的文件报出自己的 PID（0.12–0.23 秒），跨进程也认（子进程独占打开 → 报对 PID；杀掉后立刻归 0）。**不需要管理员**：用 `runas /trustlevel:0x20000` 造的真·非管理员令牌照样点出了管理员进程持有的锁 |
| 文件夹被占用 | **不能直接传目录**：传目录路径 `RmGetList` 直接回 `ERROR_ACCESS_DENIED(5)`，而且**污染整批**（目录 + 锁着的文件一起传，连那个文件也不报了）。所以实现里改成"自己枚举文件夹里第一层的文件再查" —— 实测命中，0.13 秒 |
| 一个坏路径会不会毁掉整批 | **会**。含非法字符的路径、`kernel32.dll` 这类"人人都在用的 DLL"会让整批回 0 结果 + 错误码（实测撞到文档里没写的 `ERROR_INVALID_HANDLE(6)`）。所以实现里加了**整批失败 → 逐个文件重试**（上限 80 个）来隔离坏的那个 |
| `ExtendedSubCommandsKey` 级联在 Win10 22H2 经典菜单里生效吗 | 结构按微软文档写完、四个位置共用一份子项键，`rightmenu status` 读得回来；装 / 卸的键结构由 Test-Cli 的 M15–M21 盯着。**是否真出现在菜单里要人眼确认一次**（见 §14.10） |
| 多选文件时命令被调用几次 | 用 `MultiSelectModel=Player`（一个批次一次调用，`%1` 给选中的路径）。这一条同样要人眼确认一次 |
| 改完注册表资源管理器是否立刻刷新菜单 | 一般立刻生效；万一不出现，说明里给了"注销一次"的排查路径（不要求重启电脑） |

**v1.5.1 补测的（都是修用户报的两个 bug 时量出来的）**

| 待验的 | 结论 |
| --- | --- |
| 一次查询要多少钱 | 单文件 RM 会话 **≈11ms**（锁着的 11.58ms / 没锁的 9.82ms，各 100 次平均）；**60 个文件一批只要 10ms** —— 和查 1 个一样。所以"先批量判有没有、命中再逐个文件定位"这条路是划算的 |
| "到底有没有被占着"能不能给确定答案 | **能**，`FileStream(ReadWrite, FileShare.None)` 一试就知道：被占用回 `0x80070020`（共享冲突），权限 / 只读回 `0x80070005`（`kernel32.dll` 就是后者），能打开就是真没人在用 |
| 文件夹本身能不能这么试 | **能**，但要 `CreateFile` + `dwShareMode=0` + `FILE_FLAG_BACKUP_SEMANTICS`：`C:\Windows\System32` 回 `err=32`（有人占着它）、普通临时目录回成功。不带 `BACKUP_SEMANTICS` 一律"拒绝访问" |
| 「文件夹第一层只有子文件夹」会怎样（用户报的场景） | v1.5.0 **直接放弃**：`error=这是个文件夹，而且里面没有文件可以查`。v1.5.1 往下扫之后：`scanned=1 hits=1`，并指名 `file=…\年报资料\Q3报告.docx`、`pid=4172`（持锁的子进程），pid 对得上 |
| 菜单图标为什么是空白 | 注册表里写的是 `Icon="…\Mxx1Toolbox.exe"`，而 `build.ps1` 的 `/win32icon:` 因为 **`assets\app.ico` 根本不存在**从来没生效 → exe 没有图标资源 → 菜单项空白。转成 `.ico` 之后 8 个父键全部指向真实存在的 `.ico`（测试读文件头 `00 00 01 00` 核对），子菜单 15/15 项也都有 |
| 沙箱里量 RM 有个假象 | 本会话的受限令牌**子进程**持有的锁，RM 有时看不见（同一个文件用系统进程持有的锁就看得见：`explorer.exe` 占 `thumbcache_32.db`、4 个 `svchost` 占 `System.evtx` 都报得准）。所以"查不到"要先用**本来就存在的占用**复核，别拿自己起的子进程当唯一判据（§12.46 那个不等待的坑还会再骗你一次） |

### 14.9 这台机器上的右键菜单管理器（Context Menu Manager Plus）

用户 2026-10-04 提醒「我电脑装了 Context Menu Manager Plus，你给的叫我审核」。查清了它的机制：

- 安装位置 `D:\Context Menu Manager Plus\`（v1.6.8），带一个常驻服务
  `ContextMenuManagerPlusService` + shell 扩展 `{004B0726-A010-4ABF-8556-FCDB7F1FCA1E}`，
  数据目录 `C:\ProgramData\ContextMenuMgr\`。
- `backend-protection-settings.json` 里有个开关 **`lockNewContextMenuItems`**：开着的时候
  **新装进右键的项会进它的「待审核」列表**，不去它那里放行就不会出现在右键里（这就是"审核"）。
  这台机器上现在是关的（新装的项直接生效）。
- `context-menu-state.json` 里逐项记着 `isPendingApproval` / `desiredEnabled` / `observedEnabled`
  / `onlyWithShift` 等状态（这台机器 71 项里当时有 5 项是待审核）。

所以工具箱的「右键菜单状态」会**主动念出它的态度**（装了没有、版本、锁定开关是开是关、
我们这几项被它标成待审核没有），不让用户对着"装了但右键里没有"发懵。检测在
`RightMenu.CcmpNote()` 里，路径由系统文件夹拼出来，**代码里不写本机绝对路径**。

1. 右键菜单里**真的出现了**「解除文件占用」「一键解除占用」和「常用功能」（含 Win11 需要点
   「显示更多选项」、或去 Context Menu Manager Plus 放行）；
2. 多选几个文件时点它，命令是**调用一次还是每个文件一次**（决定 `MultiSelectModel` 要不要改）；

所以写在文档里而不是假装测过。

### 14.7 底线（和隐私 / 常用设置同一套）

1. 只碰 `Mxx1*` 这些自己写的键，**一个别的键都不动**（特别是隔壁「永久删除」的 verb）；
2. 写之前记原值，撤掉 = 按记录还原；
3. 结束进程只结束勾选的，系统关键进程禁止勾选，不做句柄级强杀；
4. 查不到占用就如实说，不谎报成功；
5. 界面里"会改动系统"的动作必须过 `MainForm.EnsureAccepted()` 那套确认；命令行不提供写入口
   （唯一的例外是 `rightmenu unlock --auto`，代价是它自己那条线更窄：见第 6 条）；
6. **「一键解除占用」没有确认框，所以它的底线单独写死**（只有 `FileLock.AutoUnlockTarget` 一处）：
   只结束"真占着文件的"和"它自己正在运行"这两类；系统关键进程 / `explorer.exe` / 工具箱自己一律不动；
   "窗口里开着它"的也不动；**没同意过使用条款就一个进程都不碰**；干了什么全写日志（§14.14）。

### 14.11 v1.5.1：用户报的两个问题（根因 → 修法 → 怎么盯）

用户 2026-10-04 装完 v1.5.0 之后的原话：**「解除文件占用效果不行，没有扫描到占用文件」**
**「刚刚加进去的右键功能没有图标」**。追问出两个关键信息：他是**右键一个文件夹**，
而占着文件的是 **Office / 记事本 / PDF 阅读器**。

| 问题 | 根因 | 修法 | 谁盯着 |
| --- | --- | --- | --- |
| 右键文件夹扫不到占用 | `WhoLocks` 只枚举文件夹**第一层**的文件；第一层全是子文件夹时 `resources.Count == 0` → 直接返回"里面没有文件可以查"。而"右键一个项目 / 资料文件夹、占用它的是子文件夹里那个 Word 文档"正是最常见用法 | 改成 BFS 往下扫（深度 ≤4、≤400 个文件、跳过软链接、总时长 ≤4 秒）；整批失败二分劈开重查；命中后逐个文件定位到具体文件；窗口多一列「占着的文件」 | M14d（CLI）+ N06（窗口） |
| 查不到时只说"查不到" | 窗口里只有一句"没查到占用它的程序"+ 一段静态的可能原因，用户分不清"真没人在用"和"工具没查出来" | 新增 `FileLock.SelfCheck`：自己试着独占打开（文件）或独占打开目录（`CreateFile`+`share=0`+`BACKUP_SEMANTICS`），按结果分四种话说清楚 | M14b + M14c |
| 菜单项没有图标 | `Icon` 写的是 `Mxx1Toolbox.exe`，而那个 exe **没有 `/win32icon`**（`assets\app.ico` 不存在）→ 空白。注册表的 `Icon` 也不认 `.png` | 新增 `src\MenuIcons.cs`：把内嵌的按钮 PNG 现转成多尺寸 `.ico` 写到用户目录，父项 + 子菜单每一项都写 `Icon` 并读回核对 | M20a / M20b |
| （顺带发现的）背景位置参数错 | 「文件夹里的空白处」和「桌面空白处」的命令写的是 `%1`，而这两个位置资源管理器**不替换 `%1`** → 传进来的是字面量 `%1` → "路径不存在" | `RightMenuLocation.Placeholder` 按位置给 `%1` / `%V` | M16 + M14c |
| 旧版装出来的键怎么修 | 用户已经装过一次，不能让"修好了但得他自己想到去点装上" | `SyncIfInstalled` 除了重建子菜单，还把**自己写的那几个键**修补到当前版本；主窗口启动时也调一次（`MXX1_NO_RIGHTMENU_SYNC=1` 可关，界面回归测试用它） | M20c |

### 14.12 v1.5.2：另外两种占用情况 + 结束进程连子进程 + 句柄级「强制解锁」（照火绒那套）

用户 2026-10-04 的第二轮反馈：「**右键文件夹说有程序占用着但找不到进程**」、
「**右键 sitemap.txt 说没找到**」、「**结束进程之后窗口没关掉**」，然后又问了一句
「**火绒的解除文件占用是怎么做的？**」—— 最后定了要照火绒那套加一个「强制解锁」。

#### 除了「谁占着」，还要说的两件事（都是"便宜且准"的查法，不是猜）

| 要说的 | 为什么要它 | 怎么查 | 谁盯着 |
| --- | --- | --- | --- |
| **它自己在运行** | 正在运行的程序**不持有文件句柄**（可执行文件是内存映射，加载器读完就关句柄）—— Restart Manager 和"我自己独占打开试试"**都看不见它**，可它让文件删不掉、文件夹松不开。用户那个文件夹里正放着一个在跑的安装包 | Toolhelp 快照拿全进程 → `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `QueryFullProcessImageName` 拿镜像路径 → 和目标文件相等 / 在目标文件夹里（任意一层）就点名 | M14e（CLI）+ N07（窗口） |
| **窗口里开着它** | 记事本这类程序**读完就关句柄**，本来就没锁（实测：用户开着的 `sitemap.txt` 谁都锁不住）—— "没查到"其实是对的，但用户会觉得"我明明开着它，工具坏了" | `EnumWindows` 取可见顶层窗口的标题 + 类名：文件名出现在标题里（记事本 / 看图 / 播放器），或者资源管理器窗口（`CabinetWClass`）标题正好是这个文件夹名 | N07 + `open=` 行（窗口标题一并念出来） |
| **能不能删 / 能不能改名** | 这才是用户真正要问的那句。"被打开着"和"删不掉"**不是一回事**：实测用户那个文件夹 `exclude=err=32`（确实被打开着）但 `DELETE 权限=ok`（**能删能改名**）；桌面反而是真被拦 | 拿 `DELETE` 权限开一次（共享模式放开 read\|write\|delete，目录带 `FILE_FLAG_BACKUP_SEMANTICS`）：开得成 = 系统允许删除；`err=32` = 有程序拦着；`err=5` = 权限（ACL）。**正在运行的 exe 这招测不出来**（镜像文件照样能拿 DELETE 权限开），所以那条由"它自己在运行"负责说 | `candelete=` / `deletenote=`（CLI）+ 窗口结论行 |

#### 结束进程：连子进程一起（用户报的"锁解开了、窗口还在"）

- 实测现场：用户跑 `qingjian-0.1.4-...-setup.exe`，右键「结束进程」后文件锁松开了（父进程死了），
  但「青简状态条」那个窗口还在 —— 查下来 `qingjian-server.exe` 的**父进程 PID 19952 已经死了**，
  它是被安装包**拉起来的子进程**（安装包是 Inno Setup：外壳进程把自己解到 `%TEMP%\is-*.tmp` 再跑）。
- 修法：`FileLock.Kill` 先按 Toolhelp 的父子关系把目标 + **所有后代**算出来，**按层数深的先杀**
  （先子后父，顺手断掉"父进程被杀了又被守护子进程拉起来"这种回魂），子进程也要过一遍
  "系统关键进程 / 工具箱自己"的底线；确认框里把"会连带结束哪几个子进程"写出来。
- 命令行只提供**只读预览**（`child=` 行），真动手只能从界面点。

#### 句柄级「强制解锁（不关程序）」—— 照火绒那套

火绒的做法（官方教程 + 论坛）：右键「使用火绒安全软件解锁占用」→ 自动分析出锁定它的进程 →
点「全部解锁」，**程序不用关**。它靠的是**杀毒软件的内核驱动 + SYSTEM 服务**，所以能看到
System / 更高权限进程手里的句柄。我们不用驱动、不提权，走**用户态那条路**：

1. `NtQuerySystemInformation(SystemExtendedHandleInformation)` 一次拿全系统句柄表；
2. 只留"文件"类型的句柄 —— **类型编号每个系统版本都不一样**（Win11=40 / Win10=37 / Win7=28），
   所以先自己开一个 `NUL` 句柄，再从表里反查出**这台机器上**"文件"是几号（不写死版本号）；
3. 先 `GetFileType` 过滤：不是磁盘文件的（管道 / 设备）直接跳过 —— **管道句柄上查名字会阻塞**
   （社区文章原话；我自己也实测过 `GetFinalPathNameByHandle` 卡死过一次，整个进程挂住）；
4. 名字查询再套一层"**开线程 + 250ms 超时**"的保险，连着卡 5 条就收工并如实说"结果可能不全"；
5. 按"对象地址"去重（同一个文件被 10 个进程打开，名字只查一次）；
6. 路径匹配上了，就 `DuplicateHandle(..., DUPLICATE_CLOSE_SOURCE)` —— **这一句就是"解锁"**：
   它在把句柄复制到我们这边来的同时，**把源进程里的那个句柄关掉**；
7. 关之前**逐条再核对一遍路径**（句柄值会被系统回收再分配，绝不能拿旧值去关别人的别的东西）。

实测（这台机器，2026-10-04）：全表 ~4000 条文件句柄、**700–950 毫秒**扫完，零卡死；
`FileShare.ReadWrite` 共享打开的文件（RM 看不见）能查出来；目录句柄也能查出来。

已知边界（如实写在确认框和说明里，不假装万能）：
- **系统进程 / 别的用户**手里的句柄抽不动（`OpenProcess` 直接拒绝）—— 要管理员；
- **内核驱动自己持有的句柄谁都抽不掉**：火绒官方论坛原话「火绒剑无法摘除驱动句柄的」「暂不支持」；
- **风险**：句柄被从脚下抽走，那个程序可能报错 / 存不上盘 —— 所以按钮过确认框、默认不勾、
  风险写在确认框第一行；命令行**故意不提供**"关句柄"的入口（`rightmenu handles` 只读）。

谁盯着：CLI `M14g/M14h`（句柄表看得见共享打开 / 目录句柄）、GUI `N09a–N09e`
（按钮在 → 确认框写了风险 → **点执行后那个进程还活着** → **文件真的自由了** → 窗口念了结果）。

### 14.13 v1.5.2 收尾：exe 图标 + 小窗口高度自适应 + 用户可见文案的口气

用户 2026-10-04 的第三轮反馈，三句话：**「编译好的 Mxx1Toolbox.exe 没有图标」**、
**「解除文件占用里面的窗口高度没有做自适应高度」**、
**「那些提示不要做得太像AI了，明明都是固定的功能，非要说什么线索」**。

#### ① exe 自己的图标（两处都要管：资源 + 窗口）

- **根因**：`build.ps1` 里 `/win32icon:assets\app.ico` 要的那个文件**从来不存在** —— 那行等于没写。
  （v1.5.1 修右键菜单图标时就发现了"这个 exe 自己没有图标资源"，当时用"把内嵌 PNG 转成 .ico"绕开了，
  但 exe 本身还是一片空白。）
- **第一层（资源）**：`assets\app.ico`，由 `tools\Make-AppIcon.ps1` 生成 —— 圆角蓝底 + 2×2 白色圆角
  方块（"一墙按钮"，和 112 个按钮 PNG 同一套画法），**16/20/24/32/48/64/128/256 八个尺寸各画一遍**
  （不是把大图缩下来），32 位 DIB 直接拼 ICO（不写 PNG 帧：.NET 的 `Icon` 读不了 PNG 帧）。
  374 KB。`build.ps1` 缺文件时会 `Write-Warning` 喊一声，不再默默跳过。
- **第二层（窗口）**：WinForms 的窗口**不设 `Form.Icon` 就画它自带的"空白窗体"图标** ——
  所以光有资源还不够，标题栏和任务栏依旧是没图标的样子。`src\AppIcon.cs`：
  `LoadImage(hInstance, "#32512", IMAGE_ICON, cx, cy, 0)`（csc 就是把这个图标写成资源组 32512）按
  窗口要的尺寸取那一档 —— 标题栏（`ICON_SMALL`，DPI 100/125/150 分别是 16/20/24）走小图、
  任务栏 / Alt+Tab（`ICON_BIG`）走 32×32。**`Form.Icon` 属性给的是大图**（WinForms 自己重发图标时
  两边都用它，给 16px 会把任务栏那张顶成放大版），发完属性再补一次 `ICON_SMALL`，句柄建好和
  Shown 各来一次。全部 9 个窗口改从 `Mxx1Form` 派生（新加窗口不会再漏）。
- 谁盯着：CLI `A14–A17`（ico 文件 / 格式与尺寸数 / `/win32icon` 那行还在 / **exe 上按像素验**：
  蓝底 + 白色方块，.NET 默认图标一点纯白都没有）、GUI `A04b` + `N16`（主窗口和独立小窗口
  的标题栏小图 / 任务栏大图都是我们自己那张）。

#### ② 「解除文件占用」小窗口：高度按内容算，不按行数拍

- **根因**：高度是 `210 + 行数 × 20`（最多 470）—— 只算了列表，**上面那几行字一行都没算**
  （路径行、状态行、自查结论、常驻提示全都会换行）。于是行数少时窗口偏高；**"没查到占用"**时
  正文有八九行（自查结论 + 能不能删 + 为什么 + 四条可能原因），下面被切掉一半。
- **现在**：逐块量出来相加 ——
  - 文字：`TextRenderer.MeasureText(text, font, new Size(标签自己的 MaximumSize.Width, 0), WordBreak)`
    （**用标签自己的宽度**：高 DPI 下 WinForms 会把 `MaximumSize` 一起放大，用常量量出来的行数偏多）；
  - 列表：`ListViewItem.Bounds`（Details 视图里第一行的 `Top` 就是列头高度、`Height` 就是行高）——
    别按字号猜；
  - 再夹进屏幕工作区；高度变了**按原来的中心点重新摆一次**（不然只会往下长，看着就不在屏幕中间）。
- 顺手去掉那 2 秒的"空列表框"：窗口一出现先写「正在检查谁占着它……」，查完才显示列表；
  状态行统一走 `SetStatus()`（结束进程 / 强制解锁的结果都是好几行，窗口跟着长）。
- 谁盯着：GUI `N14/N15`（每个可见控件完整落在客户区 + 底部空白 ≤ 40px，**用屏幕坐标判，DPI 无关**）、
  `N17/N18`（"没查到占用"那种长正文必须完整显示、窗口跟着长高）。

#### ③ 用户可见文案：固定功能就直说，别写成"推理"（用户："不要做得太像AI了"）

- 「线索」这个词整套去掉：窗口里「……也会列出来，那是**线索**，不一定要结束」→
  「列表里还会列出「它自己在运行」和「窗口里开着它」的程序：这两种都没有锁住文件，一般不用结束」；
  状态行「下面那行是「它自己在运行」的线索」→「下面那行是「它自己在运行」的那个程序」。
- 「像 AI 在解释自己」的句子也一并改掉：
  - 「正在扫全系统句柄（像火绒那样，几秒钟）…… **这不是卡死，是在干活**」
    → 「正在检查全系统的句柄，大约几秒 —— 这一步走完会弹确认框」；
  - 「没找到**攥着**它的句柄」→「没找到打开它的句柄」；
  - 「这条结论**不是猜的**：我刚刚自己试着独占打开它，成功了」
    → 「这一条是当场试出来的：工具箱刚刚用独占方式打开过它，能打开」；
  - 强制解锁的确认框不再提火绒，直接写「和「结束选中的进程」的区别：进程不动，只关掉这几个句柄」。
- **规矩**（以后新增文案照这个来）：用户看到的每一句都写"是什么 / 会怎样 / 怎么办"，
  不写"我发现了什么线索 / 这不是猜的"这种叙述；「火绒」这类比较只留在代码注释和文档里。
  判据不是肉眼：Test-Cli 的 M14b 断言 `verdict` 里有「独占打开」，Test-Gui 的 N07 断言状态行里有
  「它自己在运行」——改文案时别把这些**功能说明词**一起删掉（删了就是假红，也会让用户看不懂是哪一种情况）。

### 14.14 v1.5.4：「一键解除占用」—— 不弹窗口的那条路（用户要的）

用户 2026-10-05 的原话：**「工具箱里面的解除文件占用功能还有没有优化的空间？或者出一个不弹出窗口的版本」**，
问清楚之后拍板：**「保留现有的功能的前提下加个不弹窗的一键解除，对应也要单独加 2 个按钮一个添加右键
一个撤销右键」**，并点名了按钮名字（**装上一键解除占用 / 撤掉一键解除占用**）。

**设计上的三条决定**：

1. **不是把原来的窗口改掉，而是**多开一条入口。原来那个"列出来让你勾"的窗口一个字节都没改 ——
   用户明确说"保留现有的功能"。两个 verb 各自的命令只差一个 `--auto`，实现共用
   （`InstallSimpleVerb` / `FileLock.Scan` / `FileLock.Kill` 都是同一份）。
2. **它不弹窗口，但也不是一声不吭**：结果用**鼠标旁边一张小卡片**说一句（`src\Balloon.cs` 的
   `NoticeForm`）。理由是用户 2026-10-04 报过「点击确认以后也没有成功或者失败的反馈」——
   完全不说话的路，过几天就会变成同一个 bug。
   ⚠️ **原来这一格写的是"系统托盘气泡"**（`NotifyIcon.ShowBalloonTip`），用户 2026-10-06 实测
   「气泡没有正常弹出，而且弹出的位置要跟随鼠标」→ 换成自己画的卡片：不抢焦点、跟着鼠标走、
   几秒自消、点一下也关。根因 / 四条规矩 / 实测的位置表见 **§12.56**。
   测试一律用 `--quiet` / `--notify=0` / `MXX1_NO_NOTIFY=1` 关掉它（测试不该在别人桌面上弹东西），
   只有 N21 那四条会故意开着它、并把鼠标挪来挪去量位置。
3. **没有确认框，所以底线必须更窄、而且只写一份**（`FileLock.AutoUnlockTarget`）：

   | 对象 | 一键解除动不动它 | 为什么 |
   | --- | --- | --- |
   | 真占着这个文件的（`lock`） | **结束**（连子进程） | 这就是它存在的意义 |
   | 它自己正在运行的（`run`，比如你要删的那个 .exe） | **结束**（连子进程） | "文件夹里放着一个正在跑的安装包"是最常见的删不掉，不管它这个功能就没用 |
   | 只在"窗口里开着它"的（`open`） | 不动 | 那种根本没锁住文件，结束纯属误伤 |
   | 系统关键进程 / `pid ≤ 4` / `svchost` / `lsass` … | 不动 | 杀了会蓝屏或掉登录 |
   | `explorer.exe` | 不动 | 结束它 = 桌面重启一次，无声无息地干这个会把用户吓一跳 |
   | 工具箱自己 | 不动 | 就是当前进程 |
   | **不是你自己账户的程序**（系统服务 / 别的用户 / TrustedInstaller） | 不动 | **看归属不看名字** —— 见 §12.57：名字黑名单在权限受限的机器上会整个失效，CI 上真出过事故 |
   | 系统报的类型是「服务」的 | 不动 | 服务多半是系统组件；用户自己的程序不会被系统报成服务 |
   | **连进程名都读不出来**的 | 不动 | 这时手里的名字是系统报的友好名，禁止名单对它无效 —— 不能拿"猜的名字"去赌 |
   | **没同意过使用条款时** | **一个都不动**（只写日志） | 这条路没有窗口可以弹确认框，规矩是"不同意就不动手" |

**实测**（写测试之前先端到端跑了一遍，都是这台机器上的真数据）：

```
$ Mxx1Toolbox.exe rightmenu unlock --auto --quiet <被 powershell 独占的文件>
auto=killed
killed=2                      ← powershell.exe + 它拉起来的 conhost.exe 都结束了
summary=已解锁：结束了 2 个程序（powershell.exe），现在应该能删 / 改名了。
（再查那个文件：lockers=0  candelete=yes）

$ ... --auto --quiet <没被占用的文件>
auto=none  killed=0  summary=没有程序占着它 —— 可以直接删 / 改名。

$ ... --auto --quiet …\System32\winevt\Logs\System.evtx     ← 永远被 4 个 svchost 服务占着
auto=locked  killed=0
（再查：占用者还是 4 个 —— 一个都没动）
```

最后那条还顺手暴露了一句话写错了：一开始它说的是"确实有东西占着它，但**报不出是哪个程序**
（多半是杀毒软件的实时扫描或驱动）"—— 明明报出来了（4 个服务），是**我们不肯动**。
现在 `AutoUnlock.NothingToDo` 的判断顺序是：真没人占 > 知道是谁但不许动 > 报不出名字。

**命令行输出是给测试读的**：`paths=` / `path=` / `auto=killed|partial|none|locked|skipped-consent|error`
/ `killed=N` / `failed=N` / `summary=…`。退出码 0 = 正常跑完（解没解开都算 0），
2 = 没给路径，1 = 这次查询本身出错。人话报告进日志（`Logger`）。

**提示卡那三个开关**（v1.5.4）：`--notify=<毫秒>` 定它显示多久（不写 = 6 秒，夹在 800ms - 60s），
`--notify=0` 和 `--quiet` 都是**不要提示卡**（`MXX1_NO_NOTIFY=1` 也行）。
回归测试一律带 `--quiet`；只有 N21 那四条故意不带，它用 `--notify=3000` 把等待时间压到 3 秒。

## 15 测试怎么跑（2026-10-04 补：别用 pwsh 跑；2026-10-06 补：分层与挑组）

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools\Test-Quick.ps1       # 提交前闸门（只跑受影响的组）
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Test-All.ps1         # 全套
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Test-Cli.ps1         # 只跑命令行回归
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Test-Cli.ps1 -Only M,N   # 只跑 M、N 两组
powershell -NoProfile -ExecutionPolicy Bypass -File tests\Test-Gui.ps1 -Skip P     # 除了 P 组都跑
```

- **必须用 Windows PowerShell（5.1）跑，而且要带 `-ExecutionPolicy Bypass`**。两个理由都是真踩过的：
  ① 套件里有 `Get-Content -Encoding Byte`（PS 7 改成了 `-AsByteStream`），用 pwsh 跑到 M20 会当场抛
  `'Byte' is not a supported encoding name` 并**中断整个套件**；
  ② `-ExecutionPolicy Bypass` 会设 `PSExecutionPolicyPreference` 环境变量、**子进程继承** ——
  M14f 那个"父进程拉个子进程"的现场就是这么起来的；不带 Bypass 时这台机器的策略是 Restricted，
  子进程 `-File child.ps1` 直接被拒 → `child=0` 假红。
- 两个套件都会把用户的 `%LOCALAPPDATA%\mxx1-toolbox\tools.json` **暂停**到 `.paused-by-*` 再复原；
  现在两边都挂了**脚本级 `trap`**（Test-Cli 原来没有），任何脚本级错误都会先把用户文件放回去。

### 15.1 分层：不是每次都要全量（2026-10-06 定的）

用户 2026-10-06 的原话：「**单独改一个功能或者添加一个功能不应该影响到其他功能，那其他功能就不用测试**」。
这个前提在按钮墙这套架构上成立（一个按钮 = 一条清单 + 一条启动路径，页签之间不共享代码），
所以"只测改动"站得住 —— 但**跨切面的体检不能省**，它们抓的正是"静默毁功能"，而且代价接近 0：

| 层 | 跑什么 | 耗时（本机实测） | 什么时候 |
| --- | --- | --- | --- |
| L0 | 编码红线体检 + 内联脚本与清单体检 | 约 5 秒 | **每次改完都跑，不商量** |
| L1 | 命令行回归里"这次改动影响得到"的组 | 4 秒 - 60 秒（看组） | 每次提交前（`tools\Test-Quick.ps1`） |
| L2 | 界面回归里映射到的组 | 约 2 分钟 | 涉及界面 / 互操作，且你没开着工具箱 |
| L3 | 命令行回归全套（207 项） | 116 秒 | 推上去之后由 CI 在 GitHub runner 上跑 |
| L4 | 全套（命令行 207 + 界面 153）+ 人眼清单 | 约 4.5 分钟 | **发版前一次** |

两条纪律：

1. **L0 永不省**：BOM 掉了中文变乱码、清单 JSON 坏了整页按钮消失 —— 这两类错误没有别的关卡能拦。
2. **没跑的组要指名写出来**（不是笼统的"没测全"），而且**发版前必须清空这份欠账**。
   2026-10-06 的 v1.5.4 就是在"界面回归没复跑"的状态下发的；那次之后才把这条写成规矩，
   并在两个套件的汇总里加了 `本次没跑的组: …` 这一行。

### 15.2 挑组执行（`-Only` / `-Skip`）

两个套件都支持 `-Only A,B` / `-Skip P`：组标记就是各自源码里那些 `# ---- X 组：…` 注释里的字母，
**前缀匹配**（`-Only A` 会带上 `A14` 那种子块）。实现是每个组外面包一层
`if (Test-GroupSelected 'A') { … }`，没选中的组整段不执行 —— 连夹具、真起进程那部分也不跑，
所以挑组是真省时间：`-Only A,E` 实测 **4 秒** vs 全套 **116 秒**。

- **公共前置**：命令行的 B/C/F/H/I/K/M/P/S 都读 A 组跑出来的 `$status` / `$WinName` 这些量，
  所以挑任何组都要带上 A（`tools\Test-Quick.ps1` 自动加，`Test-Cli.ps1` 文件头也写着）。
  界面那边的夹具都在「准备」段里（分组之前），不需要前置组。
- **`-Only` 只影响中间的检查组**：界面套件的「准备」段与「现场复原」段照旧总会跑
  （不然测试实例起不来、用户的设置也复原不了）。
- 汇总里会打印 `本次跑的组: …` 与 `本次没跑的组: …`（组名单是读自己源码里的标记得出的，
  不维护第二份名单）。挑组**不许**把真断言改成"跳过" —— 只是不跑。

**做这件事时踩到的两个坑**（都是实测出来的，教训写在代码注释里）：

1. `powershell -File x.ps1 -Only M,N` 传进来的是**一个字符串 `"M,N"`**，不是数组 ——
   第一次实测就是"挑了 A,E 却一组都没跑"（`本次跑的组:（无）`）。现在两个套件都按 `, ; 空格` 自己拆。
2. `param([string[]]$Skip)` 和 Test-Cli 里原有的**跳过计数器 `$script:Skip`** 撞名了
   （PowerShell 变量不区分大小写，`$script:Skip = 0` 把参数里的数组直接覆盖成整数 0）——
   表现是横幅打出"跳过 0"。计数器改名 `$script:SkipCount`。
   教训：**给测试脚本加参数之前先 grep 一遍同名变量**（大小写不敏感）。

### 15.3 映射表与闸门

- **映射表 `tests\test-map.json`**：`改哪块（路径通配） → 跑哪些组`。它既是数据也是文档：
  `powershell -File tools\Test-Quick.ps1 -List` 会把整张表打成人话（含每组盯什么）。
- **闸门 `tools\Test-Quick.ps1`**（约 1 分钟）：读 git 里的改动 → 查映射表 → 跑
  L0 + 编译 + `Test-Cli.ps1 -Only <组>`；界面组默认**不跑**（要你没开着工具箱），
  加 `-Gui` 才跑映射到的那几组（开着工具箱时它只打印警告，不会硬跑出一片假红）。
- 兜底规矩两条：**没命中任何规则的改动 = 跑全套**（宁多勿少）；**改测试自己 = 全套**
  （挑组机制本身也可能被改坏）。
- 映射表里写错组名 = 那一组**永远不跑**（静默漏洞），所以 `Test-Quick.ps1` 会拿套件里真实的组标记
  校验一遍，对不上直接失败。
- **"哪些组没跑到"按前缀算**：两个套件都是**前缀匹配**（`-Only A` 连带跑 A14），所以只要有一个
  选中的组是它的前缀就算跑到了。原来写成 `-notcontains`，于是 `-Only A,B,…` 时会把 A14 列进
  「本次不跑」——**假欠账**，会让人白跑一次 `-Full`（实测踩到，见下）。

**闸门自己的三个毛病（2026-10-06 补完最小化那一轮时全踩到了，都已修）**

| 毛病 | 根因 | 症状 | 修法 |
| --- | --- | --- | --- |
| **读不出改动 → 静默退回全套跑** | 脚本开头 `$ErrorActionPreference='Stop'`，而 **PowerShell 5.1 在 Stop 下会把原生命令写到 stderr 的每一行当成终止性错误**：git 只要工作区里有 CRLF 差异就会写 `warning: … CRLF will be replaced by LF …`，**`2>$null` 也拦不住** → 命令中断、`$LASTEXITCODE` 变 `-1`、改动集读成空 | 每次都报「自动读不出改动」，然后按全套跑。表面"宁多勿少"很安全，**实际把映射表整个架空**，报出来的原因还是误导的 | `Get-ChangedPaths` 里临时把 EAP 放成 `Continue`（函数作用域），并分别检查两次 git 的退出码；读不出时把**真实原因**打出来 |
| **每段测试的输出全被吞掉** | `[void](Invoke-Stage …)`：子进程 stdout 进的是函数的输出流，被 `[void]` 一起丢掉 | 跑两分钟屏幕上一片安静（像卡住），失败时只剩一句「闸门没过：命令行回归」，没有细节可查 | `& $hostExe @argv \| Write-Host`（`[void]` 就只吞退出码） |
| **假欠账「A14 没跑」** | "没跑的组"用了 `-notcontains`，没跟前缀匹配对齐 | 明明跑了却被记成欠账 | `Test-CoveredBy`（前缀比对） |

第一条最阴：它**不报错、不失败**，只是悄悄把整套挑组机制变成"永远全量"。所以给
`tools\Test-InlineSyntax.ps1`（L0，每次改动都跑）加了一段**真跑自检**：造一个**假 git**
（`git.cmd`：先往 stderr 写一行 CRLF warning，再往 stdout 报一个文件名），用 AST 把
`Get-ChangedPaths` 抠出来在**子进程里带 `$ErrorActionPreference='Stop'`** 跑一遍 ——
读得出那个文件名才算过。自检的灵敏度也验过：把 EAP 那道防线摘掉，输出立刻变成 `COUNT=0`。

### 15.4 流程约定（2026-10-06 用户拍板）

1. **本地随便提交，推送要用户点头**（原话：「本地推送可以线上推送得经过我点头」）。
2. **每次汇报带一行「未推送提交」**（`git log origin/main..HEAD --oneline` 的真实输出，别手写状态）。
3. 提交信息写四段：**改了什么 / 为什么 / 我验了什么 / 我没验什么**。
4. 提交前跑 `tools\Test-Quick.ps1`（L0 + 受影响的组）；汇报里指名跳过了哪些组。

## 16 兼容性与发布环境（Win7 / Win10 / Win11）

> 2026-10-05 用户拍板：**「兼容只需要考虑 win7 win10 win11 就行了」**（比"所有 Windows"窄）。
> 这一节就是这三版上的逐项结论，以及"能在这三版上跑同一套测试"的做法。

### 16.1 运行环境（先决条件，不是工具箱能拦的）

| 系统 | 先决条件 | 说明 |
| --- | --- | --- |
| **Windows 10 / 11** | 无（系统自带 .NET Framework 4.8） | 拷过去双击就能跑 |
| **Windows 7** | **SP1 + 自己装一遍 .NET Framework 4.x** | 用系统自带的 `csc` v4.0.30319 编译 → 这就是个 4.x 程序；Win7 自带的只有 3.5，**没装 4.x 时双击 exe 会得到系统那句"需要 .NET Framework"的提示**，不是工具箱崩了 |

exe 是 **anycpu**：64 位系统按 64 位跑，32 位系统按 32 位跑（所以下面的句柄表那条才要紧）。

### 16.2 逐项结论（哪些行会因系统版本而不同）

| 位置 | Win7 | Win10 | Win11 | 处理 |
| --- | --- | --- | --- | --- |
| 字体（微软雅黑 / Consolas） | 有（Vista 起） | 有 | 有 | 不用管 |
| DPI（System DPI aware + `AutoScaleMode.Font`） | 认 | 认 | 认 | 不用管（PerMonitorV2 要 exe.config，会破坏"单文件"） |
| `longPathAware` | 忽略 | 认 | 认 | 留着，老系统忽略不影响 |
| `supportedOS` 清单 | **必须写** | 必须写 | 同 Win10 | 写齐 7 / 8 / 8.1 / 10（漏了 Win7 那条 → 老系统按兼容模式对待程序，而且 `GetVersionEx` 会撒谎） |
| `Environment.OSVersion` | 6.1 | 10.0.19041+ | 10.0.22000+ | `Launcher.WindowsName()` 据此报 `windows=`；**判据不是它一个**（见下） |
| 深色标题栏（`DwmSetWindowAttribute` 19/20） | 不生效 | 1809+ 生效 | 生效 | 安静地退回浅色标题栏，界面其余照旧 |
| 句柄表条目布局（强制解锁） | x86 28 / x64 40 字节 | 同左 | 同左 | 按 `IntPtr.Size` 现算（原来写死 x64 → 32 位系统上会扫出垃圾） |
| 「文件」句柄的类型编号 | 28 | 37 | 40 | **自查**（开一个 NUL 句柄再回表里找它），不写死版本号 |
| `ms-settings:` 协议 | **没有** | 有 | 有 | `SystemTarget.HasSettingsApp`：先读 `HKCR\ms-settings`（版本号会被骗，注册表不会），读不到才退回版本号；Win7 上那 7 个按钮给"去控制面板哪儿找"那句 |
| 右键菜单（`HKCU\Software\Classes`） | 经典菜单里直接可见 | 直接可见 | **要先点「显示更多选项」** | 「右键增强说明」里写了；也可以用「经典右键菜单」按钮换回 Win10 那套 |
| Restart Manager（查占用） | 有（Vista 起） | 有 | 有 | 不用管 |
| UAC / `asInvoker` | 认 | 认 | 认 | 工具箱自己从不提权，提权只发生在单个按钮上（`runas`） |

### 16.3 怎么在这三版上验

- **没有 Win7 实机**：所以把"会随版本变"的东西全部收进**两条可断言的输出**
  （`status` 的 `windows=` 与 `settingsApp=`），测试项 `A03b` / `A03c` / `A03d` 与 `D01`
  **按这台机器是哪一版分叉断言**：Win7 上那 7 个 `ms-settings:` 按钮**必须**被算成"这台系统没有"，
  Win10 / 11 上**必须**一个都不缺。同一套测试拿到 Win7 上跑就应该全绿。
- **人工确认**（测试盯不了的）：Win7 上的深色主题外观、Win11 上右键菜单要在「显示更多选项」里点得到、
  32 位系统上「强制解锁」真能解开一个被占用的文件（本机是 64 位，只能靠偏移量的正确性推）。
- **不保证**：XP / Vista / Windows 8 / 8.1（8.1 上大概率能跑，但没测过不写进支持范围）；
  Windows Server（没测）；ARM64 上的 x86 仿真（没测）。

## 17 v1.5.3 三件套：自动按钮 / 更新检查 / 条款确认门

- **工具目录自动长按钮**：正本在 §13.7（扫什么文件夹、默认值、四条底线）。
- 下面是另外两件的设计。

### 17.1 更新检查（`src\UpdateCheck.cs`）

**三条底线**（和前两个"会联网"的功能同一套）：

1. **只读**：只拿版本号（GitHub 的 releases 接口，失败再退 tags 接口），**不下载、不替换、不写盘**；
2. **失败静默**：查不到只写日志，界面不弹窗（关于窗口的状态行写"查不成"+ 原因）；
3. **能彻底关掉**：`MXX1_NO_UPDATE=1`（`true` / `yes` / `on` 也算）之后一个字都不发。

**入口**：关于窗口一行「更新」状态 + 「检查更新」按钮；底栏发现新版本时弹一句「发现新版本 vX.Y.Z」
（点了打开发布页）；命令行 `checkupdate`（退出码 `0` = 查过了，有新版本也是 0；`1` = 关掉了 / 查不成）。

**实现要点**：强制 TLS 1.2（Win7 上不设就连不上 GitHub）；超时 `MXX1_UPDATE_TIMEOUT_MS`；
地址可换 `MXX1_UPDATE_URL` / `MXX1_UPDATE_TAGS_URL`（**测试就是靠这两个在本机起一个 HttpListener
假接口，全程不碰外网**）；`CheckAsync` 把等待期间的界面动作排在回调**之后**执行
（这个顺序 bug 就是"关于窗口永远停在正在检查…"的原因）。

**接口地址必须现推，不能拿网页地址拼**（2026-10-05 发布当天发现的真 bug）：
`https://github.com/<账号>/<仓库>/releases/latest` 是 HTML 页面，请求里带着
`Accept: application/vnd.github+json` 时 GitHub 回 **406**，于是用户那边永远是"检查失败：http-406"。
正确做法是从 `AboutForm.RepoUrl` 现推接口根：`https://github.com/A/B` →
`https://api.github.com/repos/A/B`（`UpdateCheck.MakeApiBase()`）。
**为什么两套测试没抓到**：S 组全程拿 `MXX1_UPDATE_URL` 指到本机假接口，绕开了默认值 ——
所以补了 **S01b**：只看 `checkupdate` 打出来的 `api=` 那一行（要求 `https://api.github.com/repos/…`），
**不联网也能跑**。输出里那一行 `api=` 是故意留的：排障时贴进浏览器就能分清"接口写错了"和"网络不通"。

### 17.2 免责声明与服务条款

- **正本只有一份**：`docs\DISCLAIMER.md`，`build.ps1` 用 `/resource:...,Disclaimer.md` 内嵌进 exe
  （构建时会自检资源里有它，**缺了直接报错**，不会编出一个没有条款的 exe）。
- 窗口（`src\DisclaimerForm.cs`）显示的就是内嵌的这份，`disclaimer` 命令打印**纯文本**版；
  C# 里不许再抄一份正文（抄了就会有两个版本，用户看到哪个全看运气）。
- 正文分六节：做什么 / 权限与系统位置 / 免责声明 / 数据与网络 / 服务条款 / 相关文件。
  「数据与网络」那节点明了联网只发生在更新检查、「权限与系统位置」点明了写注册表的范围与还原方式。

### 17.3 首次运行确认门（`src\Consent.cs` + `src\ConsentForm.cs`）

- **记的是指纹，不是"同意过"这个事实**：`SHA256(条款纯文本)` 的**前 8 字节 = 16 位十六进制**，
  写进 `settings.ini` 的 `AgreedDisclaimer=`，时间写 `AgreedAt=`。**正文一改，指纹就不一样 → 下次打开重新确认**
  （设计如此，改条款就必须重新征求同意）。
- **哪里拦**：① 界面启动（`MainForm.OnLoad` 最前面，没同意直接关窗口、不写注册表不联网）；
  ② 点「会改动系统」的按钮（`MainForm.RunTool` 里按 `ToolItem.WritesSystem` 判断，比如「强制解锁」、
  「结束选中的进程」、「写注册表」那类）。
- **哪里不拦**：**命令行一律不拦**（`run` / `status` / 导出…照旧能用），只在日志里留一行痕迹 ——
  脚本和自动化不该被一个界面弹窗打断。
- **命令**：`consent`（看状态：`agreed` / `required`）/ `consent --accept`（免打扰地记下同意）/
  `consent --reset`（清掉，用来现场复原）。`status` 里有 `consent=` 与 `consentAgreed=`。
- **测试怎么盯**：Text-Gui 的 I 组（27 项）真的把窗口开起来：点「不同意」必须退出、复选框没勾时
  「同意并继续」必须是禁用的、接受之后 `settings.ini` 里必须有指纹、接受之后主窗口必须能用；
  **`I10b` 关掉窗口之后记录必须还在、`I10c` 重新打开不许再弹** —— 这两条是 2026-10-05 用户报
  「每次打开都弹」之后补的（原来的 `I09` 只在窗口还开着的时候查，见 §12.53）；
  Test-Cli 的 S 组（26 项）管命令行的三种用法 + 指纹一致 + 命令行不被拦。**两套测试都要在收尾时
  把用户的同意状态原样复原**（所以用户可能在下一次打开界面时看到一次确认框 —— 这是预期的）。

### 17.4 用户可见文案的口气（这一轮又重申了一遍）

用户明确说过不喜欢"AI 味"的措辞（尤其是**「线索」**这个词）。这条已经落进测试断言里：
界面和命令行里凡是解释"谁占着这个文件"的地方，都必须写成
**「它自己在运行」「窗口里开着它」「查到 N 个程序占着它」「独占打开」** 这种直白说法；
测试直接断言这几个词在不在（`M` 组 / `S` 组）。
写新文案时的标准就一条：**说清发生了什么、怎么做的、需要用户做什么**，不写"检测到可能存在"。
